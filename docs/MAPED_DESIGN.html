ToriRSEd: the game and map editor for OSRS-Content

One editor server owns every document and every undo step. Any number of windows, native or browser tabs, mirror it with their own cameras. Save writes text into the content tree, RUN builds the packs and reloads the live server and its clients.

Written 2026-10-30 against v3 at 076f80db6. Audience: engineers building this in the tree. Every path is relative to the repo root; OSRS-Content paths are under OSRS-Content/osrs-content/.

The thesis. The existing map editor is not wrong, it is narrow. Its core (an authoritative server, mirrors that apply only the server's echo, authored-not-derived documents, delta commands, a cache-free chrome) is exactly the shape the sixteen requirements need, and this design keeps it. What rotted is everything around that core: one document kind, one window, one camera, a panel that holds spawns outside the authority, no catalog beyond the loaded region, no builders, no live lane, and no build target in all. The work is to generalise the core and build the rest on it, not to start over.

Rules carried over from the comments in the tree

  • Mirrors never apply their own edit. Every change is an intent; the mirror mutates on the server's echo, the sender included (editor.h). This is what makes N windows agree.
  • Chrome reaches no cache. The editor exists to repair content, so it must open on a broken bake (editor_panel.h). Palette entries and catalog rows are content and may degrade to ids; the frame around them never does.
  • Save writes text, never the cache. Only dirty halves are written, atomically. Baking is a separate explicit action and is wired to nothing else.
  • Commands carry authored records. Undo on a procedurally heighted tile must restore absence.
  • Codecs are byte-exact or a save diffs files the user never touched. Every new codec in this design gets the same whole-tree round-trip test editor_jm2_test.c has.
  • Generated files are never hand-edited. Spawns go to server/scripts/areas/edited/, never the generated areas/world/. Every generator in this design writes into a directory it owns and marks its output.

Why the authority is a separate process even when it is embedded

The embed path (torirs_maped_embed.h) runs the server inside the main window's process over in-memory queues and exercises the real wire protocol. That stays the default for a single-window session, because it needs no daemon. The moment a second window is spawned, the main window's embedded server becomes the daemon other windows connect to: Editor_HostOpenMapEdEmbedPeer already lets a process hold several connections, and the embed can expose its listening socket the same way the game server's embed exposes a party link. A viewer that crashes never takes the document with it, and a viewer on another machine (the NUC, a phone's browser) is the same connection as a local one.

3Documents and commands

Today the document is a set of map squares. The editor needs to edit seven kinds of thing, all of them text in the content tree. One abstraction covers them: a document is a path-addressed text blob under the content root with a kind-specific codec, an authored in-memory record, a derived view for rendering, and a dirty flag. The command envelope

The v1 wire sends a fixed 144-byte Editor_Cmd. v2 keeps [u32 type][u32 length] framing and makes REQ_CMD carry [u32 doc_kind][u32 doc_key_len][key][kind payload]. Fixed-size payloads stay fixed-size per kind; text splices are variable. A mirror that does not know a kind applies nothing and asks for a resync of that document, which keeps an old viewer safe against a newer controller.

struct Editor_Cmd
{
    enum Editor_DocKind doc_kind;     /* SQUARE, SPAWN, CFG, IFACE, TEXT */
    char doc_key[128];                /* "m50_50", "loc:newbie_door1", "if:bank", "rs2:edited/doors/my_door.rs2" */
    enum Editor_CmdKind kind;         /* TILE, LOC, SPAWN, SPAWN_SUPPRESS, CFG_FIELD, CFG_BLOCK, IF_FIELD, IF_COMPONENT, TEXT_SPLICE */
    union { ...per-kind before/after pairs... } u;
};

Undo is still one history on the server, grouped by stroke. A builder regeneration (one dialogue edit that rewrites an .rs2 file and a .npc overlay) is one stroke, so it undoes as one step. Editor_CmdRebuildSpan generalises to "what must re-derive": squares for TILE and LOC, the live world's spawn set for SPAWN, the record's resolver for CFG, the mounted interface for IF.

Opening documents

REQ_DOC_OPEN(kind, key) answers the authoritative current text and dirty flags, exactly as SQUARE_OPEN does today. A document stays open in the authority while any connection has it open, plus a linger, so two windows editing the same loc record see each other's field edits.

4The editing World (R1)

The runtime World is built to be looked at, not edited. The survey pinned down exactly what makes it static:

  • Terrain is one ToriDraw model per tile with the four corner heights and the lighting baked into the vertices (world_decode_tile, emitted at world_terrain.u.c 703–750).
  • The builder's per-tile maps (heightmap, blendmap, overlaymap, shape map, flag map, lightmap, sharelight, decor build map, occluder build map) exist only during the bake and are freed at RebuildCenterzoneEnd; a runtime loc spawn already needs shims because three of them are NULL afterwards.
  • A rebuild is whole-window: RebuildCenterzoneBegin clears the static pool and resets the scene. There is no per-tile invalidation.
  • Scenery of the same (loc, shape, rotation) shares one lit prototype model through ToriDraw_SceneSharedModels; placements are instances of it.
  • The World's bookkeeping arrays are fixed (events 8,192, pick 4,096, loc changes 256).

A brush drag over the border of a square today means one full square remesh per frame per square touched. That is why the current editor feels heavy, and it is the reason behind R1.

Design: two world layouts behind one builder interface

The renderer, the painter and the scene API do not change. What changes is who fills the scene and how it reacts to a change. A WorldBuilderOps vtable gets two implementations, chosen at runtime:

STATIC (the game, unchanged)

The existing path under src/engine/world_builder/. Bake, free the build maps, rebuild whole windows on REBUILD packets. Chosen by every game manifest. Nothing moves.

EDIT (new, src/engine/world_builder/edit/)

The same bake, but the build maps stay resident for the session, every tile and placement has a stable handle, and changes are applied as local invalidations with a per-frame flush. Chosen by the editor manifest ([world:boot] layout=edit) or --world-layout edit.

struct WorldBuilderOps
{
    void (*rebuild_window)(struct WorldBuilder*, ...);           /* both: full bake of the window */
    void (*tile_set)(struct WorldBuilder*, int x, int z, int level, const struct ToriRS_MapFloor* authored_derived);
    void (*loc_place)(struct WorldBuilder*, const struct World_LocPlacement*);   /* returns a stable placement handle */
    void (*loc_remove)(struct WorldBuilder*, int placement_handle);
    void (*flush)(struct WorldBuilder*);                          /* EDIT: remesh dirty tiles, relight, recollide; STATIC: no-op */
};

Stable handles

EDIT gives every placement a handle that survives flushes (the pool index plus a generation), and keeps the tile → terrain element map World_TerrainSet already maintains. Selection, ghosts and the loc editor hold handles, never element ids, so a remesh cannot orphan a selection.

Deriving from the document

The authority holds authored squares; each mirror derives. Today Editor_LoadSquare seeds the CacheProvider with derived ToriRS_MapTerrain and the load task skips a square the provider already holds. That stays as the load path. The edit path changes: a FACT_CMD TILE calls ops->tile_set with the single derived tile instead of queueing a square rebuild. Editor_DrainRebuilds becomes Editor_Flush, which calls ops->flush once per frame. The square-level derivation (Editor_SquareDeriveTerrain) remains for load and for the STATIC fallback.

Regions bigger than one window

The scene is 104×104 and the load path tops out at 64 squares. The editor does not fight that. A view is centred on a window like the game's; panning past the window edge is a REBUILD of the view's own world (the viewer owns one World), and the authority's open-document set is independent of any view's window. Two viewers can look at two continents while editing the same document set.

The server's scene

The game server keeps collision and locs per square and has no heights (torirs_server_scene.c). A saved square reaches it through RUN (§16), not through the editor world; the editor world is a preview, exactly as the current design says: "the renderer owns the world and the panel mirrors it", with the authority now where the document lives.

5Windows, views, cameras (R3, R4)

Definitions. A view is one World rendered through one camera with its own level cap, layer filters and ghost state. A window is an OS window or browser tab that hosts zero or one view plus any number of chrome panels. A client group is the set of connections acting as one editing session; the server already stores shared state per group and relays document facts to everyone.

The main window

The main window is a view with full chrome: menu bar, tool rail, catalog, inspector, builders, output console. It is what manifest_osrs242_mapeditor.ini boots today, with the panel set rebuilt (§7). It is the only window that spawns others.

Spawned windows are viewer processes

The question is whether a second view is a second OS window in the same process or a second process. The tree answers it:

  • The client is single-window by construction: one SDL_Window, one GL context, one ToriDraw scene, one painter, one cache provider, process-wide server tables. The auxiliary window is a software surface, "never a render target".
  • The web already does this with tabs, and a tab is a process from the page's point of view.
  • The plan (M7) already chose "a second process speaking the same frames over a local socket".
  • A viewer that hangs on a 68 ms frame or crashes on a bad model does not stall the authority or the main window.

So a spawned window is torirs --manifest <editor manifest> --editor-view --maped tcp://host:port --maped-group <id> --camera "x,z,level,yaw,pitch,zoom": the same binary, booted in a mode that opens no game connection, joins the main window's client group as ROLE_VIEWER, builds an EDIT world, and shows a thin ToriRSChrome toolbar (level cap, layer toggles, follow-selection, camera presets, detach/close). Natively the main window spawns it through the launch service in platform/launch_sessions.c, which already spawns the host's own binary with the host's manifest for party play. On the web the main tab calls window.open('index.html?editor_view=1&maped=wss://…&group=…'), which is what torirs_host.js already does for the viewer page.

Embedded view with extra controls versus standalone

Both are the same view code. "Embedded" is the main window's view with the full chrome around it. "Standalone" is the viewer process with the thin toolbar. A viewer can be promoted: its toolbar's "Open panels" opens the controller panels in that window too, as a second full client of the same group. There is no third kind.

Input routing

Each window owns its keyboard, which is the property the web two-tab design bought on purpose: typing a height into a panel cannot fly another window's camera. Inside one window ToriRSChrome's WantsPointer/WantsWheel arbitrate between chrome and the view, as today.

Where the server keeps state

All of it is inside struct ToriRSMapEd: documents, undo, state store, catalog index, build and live handles. No file-scope globals, which is what lets two embeds coexist and is a precondition for running the server anywhere (§17). The server still never links the cache profile or ToriDraw: deriving is the mirrors' job, so the server stays a small, portable binary.

Transports

In-process queues (embed), TCP, and WebSocket all exist in torirs_maped_main.c. Nothing new. The frame cap (16 MB) covers the largest document text.

7Chrome: baked assets and new widgets (R2)

ToriRSChrome is the only chrome. Its skin is 30 baked sprites extracted from the OSRS cache by spritebake into src/engine/torirs_chrome_skin_baked.c; its fonts are three cache fonts baked at 1x, 2x, 3x; its executors render the same retained model into a software surface, an SDL window, the web DOM bundle, or a native browser pane. The editor adds widgets and slots to this; it adds no second chrome and loads nothing from the cache at runtime.

The baking pipeline for a new visual element

  1. Find the source sprite: 3rd/rscache/tools/spritebake/spritebake --rev osrs241 cache.osrs241 --list and --probe name,.... Per the memory note, probe the full name; frame names with commas split.
  2. If no cache sprite fits, synthesise from one that does: tools/chrome_button_stamp.py stamps a glyph onto a borrowed plate (that is how the pop-out and dock buttons exist today); spritebake --disc Plate=Symbol:glyph draws a named 15×15 glyph table (k_disc_glyphs in spritebake/main.c) on a world-map disc's plate, in inks sampled from the cache's own discs, with the ring-ink strokes carrying the shape so the 2× mask route keeps it (that is how the tool rail's marquee, chevrons, ground profiles, figure, road, crates, stroke, loop, broom and the Palette's pipette exist, 2026-11-07).
  3. Append --sprite ARCHIVE[.FRAME]=Symbol[@x,y,w,h] to the recipe in the baked file's header and re-run with --out src/engine/torirs_chrome_skin_baked.c --header … --sheet sheet.bmp. Order is slot index.
  4. Add the slot to enum ToriRSChromeSkinSlot at the same index, bump the count, add the pin in src/ui/torirs_chrome_skin.h (the static asserts catch a wrong order).
  5. Regenerate the web skin: tools/spritebake_png.py into res/plugin_chrome/skin/. Fonts are unchanged unless a size is added.
  6. Add a makefile target chrome-skin that runs steps 3 and 5 from the recipe, so the bake is reproducible rather than a comment. Today there is none.

New square

A New button in the picker asks two things before anything is written:

  1. Where it lives: the coordinates (picked by clicking an empty cell or typed), and the storage: the content tree's maps/ (the default, which the cache pack reads), or a lane directory (ported/<lane>/maps/, for content that ships behind a lane descriptor). 11Loc interaction builder (R10)

A loc interaction in this tree is a .rs2 trigger block ([oploc1,name] … [oploc5], [oplocu], [aploc1] …) plus the server overlay block that gives the loc its server fields (category=, param=). The builder is a form that owns both and emits them.

Ownership

Builder output lives under a directory the builder owns: server/scripts/edited/<subject>/scripts/<subject>.rs2 and server/scripts/edited/<subject>/configs/<subject>.loc. Each generated file opens with a header naming the builder and the model it was generated from. The model is the builder's own structured record, stored as an INI block in server/scripts/edited/<subject>/<subject>.interaction; the .rs2 is derived from it. Re-opening the builder reads the model, never parses the script. A Detach button deletes the model and the header so the script becomes hand-authored. The server loader ignores .interaction files (it reads only the extensions it knows).

A loc that already has a hand-authored trigger elsewhere is shown read-only in the builder with "open the script", because sscompile refuses duplicate triggers and the builder must not create one.

The form

  • Subject: the loc, with its cache op1..op5 names as the trigger labels. Renaming an op edits the cache record's opN= field (a CFG_FIELD on all.loc), and the builder warns that this changes the client-visible menu and needs a client cache pack.
  • Per op: approach or operate (aploc vs oploc), and a list of steps. Steps are the vocabulary the tree already uses most, each a template with typed parameters: message (mes), conditional on a var (if (%var … ) with the var picker), set var, give or take obj with a count, require obj or level, open interface (if_openmain / if_opensub with the interface picker), play anim and sound (anim, sound_synth), teleport (p_telejump), delay (p_delay), loc swap (loc_change to another loc for N ticks), door via the door_closed/door_opened category pair with param=next_loc_stage (so a door is two field edits, not a script), ladder or stairs via the maplink lane, run a proc or jump to a label by name (free text, checked against the index), raw RuneScript (an escape hatch, kept verbatim).
  • Use-on: [oplocu,name] with the held obj as a condition, same steps.
  • Server fields: category, params, from the overlay block, with the field register from fields/loc.ini saying which side a field reaches.

Multilocs

A multiloc shell is multivarbit= or multivarp= plus multiloc1..N, 1-based in the text, value N selecting multiloc<N+1>, -1 hidden, the last entry the default for any value past the list. The shell editor shows the slots as a table with the value column computed, a child picker per slot, "none" for hidden, and the default row marked. Changing the var opens the var editor (§13) in place. The preview control sets STATE_VAR_PREVIEW so every view resolves the shell with VarPManager_ResolveTransform and shows the child, including the hidden case. Interactions bind to the shell or to a child; the index lists both and the builder says which the game's dispatch will hit (child category beats base trigger, per the Plague City notes).

Validation

Every regeneration runs sscompile --dry-run on the unit (the incremental compiler answers in well under a second) and shows errors inline. Save does not require a clean compile; RUN does.

The server half (.varp overlays under server/scripts/, fields/varp.ini) carries transmit, scope, protect. Names carry kind and id: varp29_cookquest, varb346_golem_a, enforced by lint and by tools/var_prefix_names.py.

The panel

The live link

The editor server attaches to a game server in one of two ways. Launch: it starts torirsserver, js5_server and io_server itself with the editor's content dir and the live cache dir, the way make web's servers run, and owns their lifetime. Attach: it connects to a running server by address (the NUC). Either way the link is a control connection the game server does not have today: a small admin protocol on the game port, selected by first byte like JS5 is, gated by the same ticket io_gate.c issues (TORIRSSERVER_GATE) so a stray connection cannot reload a public world. Its verbs: STATUS, RELOAD(diff), CHEAT(player, line) (which runs the ordinary :: debugproc path ToriRSServer_ScriptsRunDebugproc), SUBSCRIBE(varps of player) for the live inspector.

Server reload: implementing the contract

docs/serverpack.md §"The hot-reload contract" is the spec. In order:

  1. Scripts. Read the new manifest under the shared pack lock; diff script hashes. Load changed and new scripts into a new table; keep old script objects alive by refcount for parked and queued instances; swap trigger lookups and new invocations at the tick boundary. Ids are stable, so unchanged callers keep working. Signature changes are safe because the build recompiled every caller in the same pack. This replaces the "once per world" guard in ToriRSServer_ScriptsLoad with a load-into-shadow-then-swap.
  2. Config groups. For every changed server-pack archive, re-read that group and replace the records in the type's table at the tick boundary. Entities hold ids, not record pointers.
  3. Map squares. Promote ToriRSServer_SceneDebugReloadSquare to a maintained ToriRSServer_SceneReloadSquares(list): re-read the squares from the live cache, restamp collision and locs, then mark rebuild_pending for every player whose window covers them so the existing barrier sends REBUILD with the reload flag set (w239_rebuild_region already carries it).
  4. Spawns. The contract lists spawns as not reloadable because they are boot-time text. The editor needs them most of all, so: re-parse only the edited lane's changed files, diff against the current spawn set, despawn removed and spawn added statically. The generated lane stays boot-only.
  5. Not reloadable (fields, content.ini, the content loader's symbol tables, .constant values read as text): the server answers restart-needed with the list, and the editor offers Restart, which for a launched lane is one click and for an attached lane is a message.

Client reload

Clients learn about changes two ways. Map squares come through REBUILD, which already makes the client reload the window; with reload=1 the client drops its cached copies of those map archives before refetching. For everything else the game protocol has no "your cache changed" message, because Jagex ships caches at logout. It is not added to the protocol: no opcode table gains a prot Jagex never sent. The server reaches the client's control channel through the control escape (src/net/torirs_control.h): the opcode value 0x7FFF, which no revision's table comes near, then the bytes TORI, then a frame in the control link's own format (u32 type, u32 length, payload). Its message CACHE_INVALIDATE(index, count, archive ids…) goes out on the player's own connection just before the REBUILD the reload owes, so the client applies it first. The client: forgets those archives in its sparse dat2 and the IndexedDB store, re-primes the affected reference table from JS5 (the metadata-prime path already exists at boot), evicts the decoded records from the provider, and then for interfaces re-opens any mounted interface in the list, for CS2 re-fetches the script, for loc/npc/obj records re-resolves the entities on screen (the varp-driven remorph path already re-resolves shells; this reuses it with "all"), for maps triggers the normal rebuild. The JS5 server picks up the new dat2 by itself: it re-stats once a second and swaps its store.

Only a client that asked is sent a control frame: ours writes the login header's subVersion as TORI, which no stock client sends. Any other client is sent nothing and sees the change at its next login, which is what happens today.

The live inspector

With a link attached, the main window gains a Live panel: players online, the followed player's position and var values (live-updated through SUBSCRIBE), a cheat line, "teleport me to the selection", "teleport me to this spawn", and the stale-unit banner the server prints at boot shown as a list that RUN will clear. STATE_LIVE_FOCUS shares the followed player across the group so a viewer window can lock its camera to them.

17The web (R6)

The editor client is the wasm build with the editor manifest, which already runs: the canvas tab holds the view and chrome, or the chrome lives in a second tab over torirs_channel.js. The editor server is the native daemon reached over its WebSocket transport. io_server serves the page; the live lane is the same servers it is on the desktop.

Designing the server "as if it could run on the web" is a discipline the current code already mostly has, made explicit:

  • The server touches files only through EditorHost. A browser host binding would store the content tree in IndexedDB or fetch it from io_server's /boot/ route; nothing in the server knows which.
  • Building and the live link go behind two more vtables, BuildRunner and LiveLink. The native bindings spawn make and open a socket. A browser binding would answer "not available here" for build and open a WebSocket for live. The protocol's capabilities bitset tells clients which actions exist, so a menu item is disabled rather than failing.
  • No process-wide state; no threads; pump-driven. Already true, and the embed test (test-editor-torirsmaped-embed) keeps it true.
  • A viewer tab has no filesystem and needs none: it derives from text the server sends.

Web limits to state plainly: the browser cannot spawn processes, so a web main tab spawns views as tabs only; the js5 server's --max-pending must be raised for a page (memory note: 65,535), and the chrome scale follows the display density as on the desktop.

18Build order

Each milestone is independently useful and has a check that fails loudly. The order puts the two things with no existing seam first, because everything else is built on them.

  1. Foundations. Editor targets into all and test-editor into the test aggregate; protocol v2 envelope with kind-tagged commands and the alias for v1 square frames; EDITOR_CMD_SPAWN with the suppression line and the loader change; editor_spawn.c with a round-trip test over the 972 generated files. Check: two embeds, one daemon, the mirror divergence assert, byte-exact spawns.
  2. EDIT world. WorldBuilderOps, the resident build maps, tile-local invalidation and flush, stable handles; the editor manifest selects it. Check: a 20-tile brush drag at the border of two squares costs under a millisecond of remesh per frame on the Mac (measure with sample, never TORIRS_PERF), and a scripted sequence of random edits followed by a full STATIC rebuild produces an identical scene (same element models and positions).
  3. Chrome growth. Capacities, VLIST, TREE, TOOLBAR, SLIDER, RADIO, MODAL, TOOLTIP, docking; the chrome-skin make target and the first batch of baked tool icons; the WEB executor replaces panel.html. Check: the existing executor tests plus a sync test per new widget; spritebake --sheet reviewed as a crop (visual verification means crops).
  4. Catalog. Server index and query, the panel with model preview, Find in world. Check: every name in every pack is reachable by search; index build time logged.
  5. Views. Viewer mode, group join, camera state keys, native spawn via the launch service, web spawn via a tab. Check: three windows, one brush stroke, three identical mirrors (the divergence assert) and three different cameras.
  6. Terrain and placement tools on the new chrome: brushes, palettes with swatches, shape thumbnails, multi-select, spawn placement in the authority.
  7. Config documents and the var editor. editor_cfg.c with a round-trip test over every all.<type> and every overlay; the inspector; varp bit map; allocation through the ledger. Check: make torirsserver-packs on a tree with one editor-made varbit packs cleanly and the server boots on it.
  8. Builders. Loc and NPC interaction forms, the dialogue graph, the .interaction model and emitters, sscompile --dry-run inline. Check: a generated Talk-to for a test NPC compiles, packs, and plays through scriptrun with the quest driver's chat.play rows.
  9. Interfaces and CS2. editor_if.c with the 982-file round trip, tree and inspector, hook picker, runner and trace, compile check. Check: an edited interface opens identically in the client from the packed cache and from the mirror.
  10. RUN. The server control link and gate, the hot-reload contract in the game server, square and spawn reload, CACHE_INVALIDATE in the client, incremental client cache pack, launched and attached lanes. Check: edit a dialogue line, RUN, and a logged-in client sees the new line on the next Talk-to without a relog; edit a tile height, RUN, the client's window rebuilds with the new height.
  11. Lanes. Export and import, save-as-new for squares and interfaces.

19Open questions and risks

  • Client cache invalidation is a protocol extension. It is the only part of the design that is not a shape the tree already has. The alternative, relog to see config changes, fails R16 for anything but scripts and map squares. The packet is ours on both ends and the spec is INI; the risk is scope creep in the client's eviction paths, which is why interfaces, CS2 and records are listed separately with the existing path each reuses.
  • Hot reload of scripts under parked state. The contract covers it by refcount; the ScriptsFree comment about a conversation parked across a reload walking a freed pointer is the exact bug a test must reproduce before the swap ships: a player parked in p_pausebutton during RUN must finish the old dialogue and get the new one on the next click.
  • Viewer processes on one GPU. Several torirs processes each with a GL context is ordinary on macOS and Linux; on a laptop with many viewers open it is the user's memory to spend. If it proves heavy, the fallback is one process rendering several views into aux windows, which requires the renderer to become multi-target; this design does not need that and does not propose it.
  • The .if codec's unknowns. The layer= encoding and the numeric type set were not verified by the survey. The byte-exact round-trip test over all 982 files settles them mechanically and must pass before the inspector may write.
  • Generated-spawn suppression changes the loader's grammar. It is one line kind and one post-merge pass; the alternative (editing generated files) is a known data-loss bug.
  • Builder model versus hand edits. Someone will hand-edit a generated .rs2. The header says not to, Detach is one click, and the builder refuses to regenerate over a file whose hash no longer matches what it wrote, showing a diff instead.
  • Chrome capacity on the browser executor. Raising widget counts raises the DOM; the WEB executor already batches and fences, but a 4,096-widget page is to be measured, not assumed. VLIST exists to keep the real number far lower.
  • Mutation checks. Every check above that edits source to prove a test fails runs in a throwaway worktree, never in the shared tree (CLAUDE.md).
