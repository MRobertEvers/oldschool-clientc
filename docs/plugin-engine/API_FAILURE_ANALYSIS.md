# Plugin engine: visual failures and API causes

The completed evidence through candidate H is indexed in [full_visual_verification.json](full_visual_verification.json): 19 shipped feature plugins, both supported revisions, the Lua host, and the public API examples. H (`ad0f09ad349451a856080d45e49dcdfb0ee36dc4`) passed all 37 gate checks with the compatible cache-v3 fixture. Earlier detailed captures retain their original candidate and are carried forward only where the tested source paths are unchanged; H rechecks the affected native overlay and sidebar paths. Records preserve the actual stimulus, opposite control, original pixels, inspection at 2x, unsuccessful attempts and remaining limits. A test pass, a running-plugin log, or a generic pixel score alone is not visual proof.

The original [repair register](REPAIR_VERIFICATION_f7526e5b0.md) preserves all 80 audit findings and their original evidence. New findings from this review supplement it. The examples below distinguish an implementation error from a limitation or contradiction in the engine contract.

Unavailable data and unsupported features need separate treatment. A skill query can be absent because the server has not stated that skill yet; it is not an end-of-table marker. A touch-sized canvas does not prove finger input, and the desktop dummy backend cannot demonstrate a physical software keyboard. A native CS1 sidebar that is always open does not become collapsible merely because another adapter supports collapse. The final per-plugin records state these boundaries and demonstrate the supported interaction; unreached conditions remain unsuccessful attempts.

The verification fixtures preserve these distinctions: touch replay passes through the shared gesture translator and command bus; stat delay holds actual UPDATE_STAT payloads while other packets progress; role-membership and item-definition delays are explicitly service-boundary observations; long screenshot events travel through the private server's normal message packet and the client's native recognizer. The original audit worktree, cache and captures remain unchanged.


## Why another API generation is not the proposed repair

The earlier frame builder, named UI contribution registry and placement service were removed by commit `dabf74abe`. The chosen major-3 model is live widgets, native events, checked actions and explicit revalidation. Reintroducing a general declaration, placement or claim framework would revive an architecture that was deliberately rejected.

The existing [major-3 contract](CONTRACT.md) already promises coherent paint/input geometry, current native visibility, owned cleanup, native action preservation and safe callback lifetimes. Many failures above violate those promises; naming a new abstraction would not repair the shared implementation. The immediate work therefore fixes the native adapters and existing helpers, adds narrowly missing operations such as activation distinct from selection, and ties them to executable native behavior.

The meaningful acceptance change is independent evidence. Pristine bytecode must survive an actual compiler/decompiler round trip; a native lookup test must execute the real host branch; moved controls must accept actual input after native layout changes; a saved-state test must vary delivery order under the same clock; and shipped plugins must be viewed together on both revisions. Mocks remain useful for local logic, but a mock that encodes the same mistaken assumption cannot validate the contract. The incorrect intermediate opcode-203 repair is retained above as a direct example.

Higher-level helpers can reduce repeated author work once their native semantics are proven. They are not a substitute for proving those semantics, and this repair does not propose a fourth plugin API generation.
