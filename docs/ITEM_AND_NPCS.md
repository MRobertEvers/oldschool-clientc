# Where the npcs stand and what lies on the ground

The rev-239 world roster: where the list came from, how it was checked against
`cache.osrs239` before anything was written down, what the server had to change
to hold it, and how to do the same for a different revision.

| | before | after |
|---|---|---|
| npc spawns | 67 | **23,139** |
| obj spawns | 12 | **2,256** |
| distinct npcs standing somewhere | 38 | 5,597 |
| distinct objs on the ground | 8 | 343 |
| map squares with a roster | 4 (all Lumbridge) | 972 |
| files | 4 hand-authored | 972 generated |

Generated by `tools/gen_spawns.py` into
`OSRS-Content/osrs239-content/server/scripts/areas/world/configs/m<mx>_<mz>.spawn`,
with the drop report kept beside them in `spawn_report.txt`. `mock230_pack -v`
loads the tree with **0 errors** and `make -C src test-mock230` passes.

---

## 1. Why this is a lookup and not a decode

Every other kind of content in this tree comes out of the cache. Spawns cannot,
because an OldSchool cache does not contain any. Where an npc stands, how many
of it there are, and what is lying on the floor is *server* state — the client
is told about an npc when it comes within 15 tiles and never learns that it has
a home tile at all.

So the list has to be *found*, and then it has to be *checked*, because a found
list is a claim about a revision that is probably not the one in front of you.

## 2. The source, and how to tell which copy is the source

Public spawn data for modern OldSchool is all downstream of one dump taken by
walking the live game. Nobody re-derives it; everyone re-shares it, and the
copies have drifted from each other. Finding the *upstream* copy is most of the
work, because a downstream one has usually been "fixed" by somebody solving a
different problem.

**[dennisdev/rs-map-viewer](https://github.com/dennisdev/rs-map-viewer)** is the
upstream here, and it is the right place to look for a reason worth stating: it
is a *map viewer*, so it draws npcs standing on terrain across three eras and
its spawn data is a rendering input rather than a server's game state. Nothing
in it has an incentive to re-point an id at what some server wanted that id to
mean.

```
src/mapviewer/data/npc/npc-spawns-osrs.json    24,143 rows: id, name, x, y, level
src/mapviewer/data/npc/npc-spawns-2004.json    the rev-254 roster (2004scape, MIT)
src/mapviewer/data/npc/npc-spawns-2009.json    the rev-549 roster (2009scape)
src/mapviewer/data/obj/obj-spawns.json          2,266 rows: id, count, x, y, plane
```

`NpcSpawn.ts` picks between them off the cache's own identity —
`cacheInfo.game === "oldschool"`, else `revision > 474`, else 2004 — which is
the cross-revision method §7 generalises. Its `README.md` credits the halves:
**the OSRS Wiki for the item spawns**, 2004scape and 2009scape for the two
legacy npc files. The OSRS npc file is the one it does not attribute.

**Dates matter more than the credit does.** `npc-spawns-osrs.json` was last
touched **2023-08-28** and `obj-spawns.json` **2024-03-31** — so this is a dump
of a roughly rev-215 world being checked against rev 239, a gap of about two and
a half years. That gap is the entire reason §3 exists, and knowing its size is
what makes 222 drifting spawns a plausible number rather than a worrying one.

### The copy that looked equally good and was not

`xrsps/xrsps-typescript` ships the same two files (`server/data/npc-spawns.json`,
`server/gamemodes/vanilla/data/groundItemSpawnData.json`). The obj spawns are
identical row for row. The npc spawns are 24,085 rows identical, 52 dropped and
54 added — a server that hit the same id drift and re-pointed by hand.

Some of those repairs are right and some are wrong, and the wrong ones are
invisible without the cache in front of you:

## 3. The check that matters: a dump carries ids, and ids move

A spawn in this tree names its npc — `cook 3209 3215 0` — and the name resolves
through `configs/all.npc.compack`. A dump names an id. The conversion is a table
lookup and takes one line. The problem is that the lookup *always succeeds*: id
4626 is some npc in every cache ever built, so a rev-215 dump converts cleanly
against rev 239 and quietly stands the wrong creature in the wrong place.

Four gates, in order:

**1 — the id must exist in this cache.** An id past the end of `all.npc` is
dropped. 239 is a superset of the dump here, so: 0.

**2 — the name must agree.** The dump's `name` is what a player saw over the
npc's head; the cache record has a `name=`. Two refinements make the comparison
usable rather than noisy:

- *Compare the way a person would.* `<col=00ffff>Iceberg</col>` and `Iceberg`,
  `Al Kharid warrior` and `Al-Kharid warrior`, `Tea Seller` and `Tea seller` are
  the same npc. Lowercase, strip markup, strip punctuation. Without this 2,887
  rows read as drift and the real ones are invisible among them.
- *Follow `multinpc`.* A multinpc base has no `name=` — it is a shell whose varp
  or varbit picks a variant. The base id is what a server spawns; the variant is
  what a player sees. So the base is checked against **every name it can present
  as**, transitively.

  Skipping that is not a small miss. Treating "no name" as "nothing to check"
  passes npc **401** as *Turael* standing in Burthorpe, and npc 401 in this cache
  is `tog_light_creature`, a Tears of Guthix light creature. 2,518 rows land in
  this bucket; following `multinpc` turns 1,782 of them into a real comparison
  and moves 84 spawns from silently accepted to rejected.

**3 — a record with no name anywhere is kept.** 736 spawns are of records with
no `name=` and no named variant. Nothing contradicts them, so there is no basis
to drop them; they are counted separately in the report and are the one place
drift could still hide on the npc side.

**4 — the map square must exist.** A spawn on a square `cache.osrs239` does not
ship has no terrain under it. 776 npc and 9 obj dropped, almost all in the
`m56..m66_140..142` band (Varlamore) plus a stray `m0_0`.

Then: level must be 0..3, and exact duplicates collapse (6 npc, 1 obj).

### The obj half is weaker, and the report says so

The ground-item dump has **no name field**, so gate 2 cannot run on it. Only
gates 1, 3 and 4 apply to the 2,266 obj rows. An obj id reallocated between the
dump's revision and 239 is written into this tree as the wrong item and nothing
here notices. That is printed rather than hidden, and it is the first thing to
fix if a named obj dump turns up.

## 4. Grading the source against a second one

A gate proves internal consistency, not that the dump is right. For that:
`rsmod`'s hand-curated Lumbridge roster — name-based, revision-current, built by
different people from different data.

Restricted to the six map squares rsmod covers (`m49..m50_49..51`):

```
rsmod spawns in those squares:                585
rs-map-viewer spawns in those squares:        585
exact agreement (name + coord + level):       572   97.8%
coordinate agreement:                         578   98.8%
```

Seven coordinates differ by one or two tiles (Cook 3208,3215 vs 3209,3215; Duke
of Lumbridge 3210,3224 vs 3212,3220). Six more agree on the tile and pick a
different variant of the same creature — `crow2` vs `crow_lumb_patrol6`,
`farmer2` vs `farmer4`. Nothing in the sample is a different creature.

585 = 585 at 97.8% exact is not two people copying one file; the variant
disagreements prove the inputs are not identical. It is two transcriptions of
the same live world, which is the strongest statement available about a dataset
nobody can re-derive from first principles.

of the exercise: the **Tool Leprechaun** was parked beside Lumbridge castle
green because no farming patch was loaded, and is now at all 38 real patches;
Turael was parked there for the same reason. Both were marked as test placements

`mock230_pack`'s "a name qualified by another content area is beside the plain
one" warning still fires for them and is now a false positive for the honest
reason — they *are* Pest Control npcs, in Pest Control.

## 6. The server holds a window on the roster, not the roster

`mock230_world_build_entities` used to create every spawn in the tree, and the
comment defending that was right: the client is told about npcs within 15 tiles,
but the player can walk, and an npc that does not exist until you approach it
would pop into being with full hitpoints in front of you.

It cannot survive the real roster as an eager in-memory strategy. The wire is
not the reason: the **14-bit npc slot is local to one player's client and names
only nearby NPC instances**. It is neither a cache NPC id nor a world-roster
slot. The separate rev239 cache/config id field is 16 bits.

So the roster is a statement about the world and the pool is a window on to it:

| | |
|---|---|
| `MOCK230_STATIC_SPAWN_IN` = 160 | a spawn stands up when its home tile comes within 160 tiles of the scene centre |
| `MOCK230_STATIC_SPAWN_OUT` = 224 | and is retired past 224. The gap is hysteresis — with one number a player pacing across the boundary would create and destroy the same npcs every rebuild, and each cycle resets their hitpoints, aggression and `[ai_spawn]` |
| `MOCK230_NPC_MAX` = 4096 | sized against OUT, not against the roster: the densest window is 2,250 spawns (Varrock, near 3392,3328) and the rest is headroom for what content `npc_add`s |
| `MOCK230_GROUND_MAX` = 4096 | holds the **whole** obj roster. A ground obj has no wire slot — OBJ_ADD is zone state — so nothing bounds it but memory |

IN is far past what anyone can see: the scene itself is 104 tiles and the client
is told about 15, so at 160 an npc has existed for a hundred tiles' walking
before it can be looked at. That is the property the create-everything loop was
defending, kept and stated as a distance.

`world_static_npcs_sync` hangs off `mock230_world_scene_rebuild` — the one place
the window moves — and re-derives its answer from `active` and
`Mock230Npc.static_spawn` every time rather than tracking a delta, because the
pool and the roster fall out of step for reasons that are nobody's bug (an npc
dies and its slot is reused, a script removes one, `npc_spawn` declines).
`static_spawn` is `-1` for anything a script created, which is what keeps the
window from retiring npcs that are not its to retire.

Lumbridge stands **993** of the 23,139. The `mock230 selftest: the world roster
follows the scene window` case asserts the mechanism as a difference — count at
Lumbridge, move the scene to Ardougne, count again, and require the two sets to
be **disjoint**. (Ardougne rather than Varrock: Varrock is 208 tiles from the
castle and OUT is 224, so 709 Lumbridge npcs are still legitimately standing
there and the check would read as a bug in the sync.)

### Every client subscribes to the world map: `Mock230PlayerArea`

The world's `Mock230ZoneMap` is authoritative and **unbounded** — every npc, obj
and player in the game is filed in it, and nothing about it is sized to what one
client can see. What is bounded is the other end: the 7×7 zone window one client
subscribes to. Those are two structures, not one structure with a limit on it.

Before this there was no second structure. A client's view was four flat arrays,
and each of the three area packets re-derived its own candidates:

| packet | candidates from | bounded by |
|---|---|---|
| PLAYER_INFO | a walk of the whole player pool | a raw ±15 tile test |
| NPC_INFO | `mock230_zone_npcs_near`, a tile box | a raw ±15 tile box |
| zone flush | a walk of `active_zones` | the build area |

Three answers to one question, so they disagreed. Only the zone window is
clipped to the build area; a tile box is clipped to nothing. Near that edge
NPC_INFO named npcs standing outside the 104×104 region the client has a scene
for. It never fired by **one tile** — `maybe_rebuild` re-centres at
`MOCK230_REBUILD_MARGIN` (16) and the npc view was 15, two constants in two
files with nothing connecting them.

There are two zone maps now, and the names say which is which:

```c
struct Mock230ZoneMap        /* the WORLD's, authoritative, unbounded         */
    zones keyed by packed index -> { locs, objs, npcs, players }

struct Mock230PlayerZoneMap  /* one CLIENT's — a subscription, holds no entity */
    struct Mock230PlayerZone { int index; uint8_t loaded; } zones[196];
    int count;
    int built_zone_x, built_zone_z;   /* the clip this window assumed */
```

`loaded` sits **on the zone entry**, which it did not at first. It was a second
parallel array, and two arrays that must be added to and removed from together
are two arrays that can disagree — invisibly, because a zone marked loaded but
no longer subscribed is one the client is never re-told about and never updated
on. Folding it onto the entry deleted the reconciliation block at the top of
`mock230_zone_update_player` outright.

**The list is maintained; the entities in it are not.** That split is the whole
design:

- The window changes only when the player crosses a zone boundary, and then
  only at its edges — 7 columns leave, 7 enter, 42 are untouched. So
  `mock230_playerzonemap_move` is a set difference, runs in phase 8, and costs
  three compares for a player who has not changed zone. `window_holds` is the
  one place the window's shape is written down.
- What is *standing* in those zones changes constantly, so the packet builders
  walk the list when they need to know. `mock230_playerzonemap_npcs` /
  `_players` apply the plane and the view radius while collecting, **per
  entity**. Per zone is not enough and that was a real defect: a zone straddling
  the edge of the radius contributes everything in it, up to 7 tiles past the
  range, and `out` is bounded — so a dense fringe fills it with entities the
  encoder will discard and crowds out ones genuinely beside the player.

**Materialising the entity lists was tried and reverted.** Pushing membership
changes from the map into each subscriber is faster in principle and fails
silently in practice: a push that never arrives leaves a client missing an npc
standing in front of it with nothing anywhere to say so. Building it surfaced
three real bugs (below), and then the walk turned out to cost a few hundred hash
probes per tick at `MOCK230_PLAYER_MAX` clients — so the version that cannot be
stale won. The bugs were kept.

Five things fell out, and three were latent defects:

- **Players joined the ZoneMap.** Zones tracked npcs and objs and not players,
  which is why PLAYER_INFO had to scan the pool. `refile`'s `is_npc` boolean
  became `enum Mock230ZoneKind`.
- **The window depends on the build area too**, not just the player's zone.
  Re-centring the scene moves the clip under a standing player. Every re-centre
  happens to call `mock230_zone_player_reset`, so it worked by accident;
  `built_zone_x`/`built_zone_z` make the dependency the thing that is checked.
- **`npc_spawn` now unfiles the slot it is about to reuse**, which
  `mock230_zone.h` has always asked pool allocators to do. Every path that frees
  an npc clears `active` and not all of them refile; the tick's reconcile papers
  over that because it only sees the end state, and cannot when a slot is freed
  and re-handed inside one tick. This was live — a retired roster npc sat in a
  client's view under the *next* spawn's identity.
- **Logout clears the subscription.** A pid is a pool index, so a subscription
  left behind is inherited by whoever logs into that slot next.
- **`zone_index` vs `built_zone_*`.** The first is the "have I moved" latch,
  reset to -1 on every scene rebuild; the second is what the window was clipped
  against. Conflating them is how a stale window survives a re-centre.

A compile-time assertion states
`MOCK230_NPC_VIEW_TILES < MOCK230_REBUILD_MARGIN` so the margin cannot silently
close.

`mock230 selftest: NPC_INFO tracks only the player's own zones` asserts that
everything the area yields stands in a zone it subscribes to and is on the
player's plane, and that everything the client ends up *tracking* is inside the
build area. It has to **build** the edge case rather than walk to one, because a
player who walks to the boundary is re-centred before the view can overhang.
Every check was verified by mutating the implementation:

| mutation | what the suite said |
|---|---|
| drop the build-area clip in `window_holds` | `inside the build area the client has a scene for, 2 do not` |
| drop the plane filter in `area_entities` | `on the player's own plane, 1 do not` |
| drop the per-entity radius filter | `within the radius asked for, 12 are not` |
| carry no `loaded` flag across a window move | `the shot must reach the client as a MAP_PROJANIM …, got 0` |
| (pre-refactor) `mock230_zone_npcs_near` | `every tracked npc should stand in a zone the player holds, 14 of 29 do not` |

The per-entity radius row is there because the first version of that check did
not exist: the mutation passed, which is how the gap was found. `mock230_zone_npcs_near`
is gone — it had no callers left once both encoders read the client's own map.

### Two index spaces, and which one limits what

NPC_INFO carries two numbers for an npc, and conflating them is how "the wire is
14 bits, so only 16k npcs can be near a player" gets said. The authority is the
official RuneLite deob of rev 239 (`Statics.java:53065`):

```java
byte var20 = 16;                                    // index width
int var21 = 1 << var20;                             // 65536
if (buffer.readableBits(...) < var20 + 12) break;   // 16 + 12 guard
int var22 = buffer.gBits(var20);                    // 16-bit index
if (var21 - 1 == var22) break;                      // terminator 0xFFFF
class112 npc = map.get(var22);                      // keyed by the index
...
class422 type = getNpcType(buffer.gBits(14));       // 14-bit TYPE
```

| | the **index** | the **type** | the **list position** |
|---|---|---|---|
| width | 16 bits (v5), 14 (classic) | 14 bits | 8-bit count, then bits *in order* |
| means | what this client calls the npc | its config/cache id | where it sits in the tracked list |
| bounds | how many npcs one client can hold names for | how many npc records can exist | how many one client may **track** |
| here | `MOCK230_CLIENT_NPC_SLOTS` | `MOCK230_NPC_TYPE_MAX` | `MOCK230_TRACKED_NPC_MAX`, 255 |

**The index is a per-client name, not the world's slot.** The deob keys a *map*
on it — nothing requires it to mean anything globally, only to be stable while
this client is being told about the npc and unique among the npcs it holds. So
`struct Mock230PlayerSlotMap` translates at the wire and nowhere else: the
server keeps its own slot in the pool, the ZoneMap and every interaction, and
the two sites that write an id go through `mock230_slotmap_acquire` /
`_release`. The world pool's size stops being a protocol question.

**A config id above 16,383 rides in CHANGE_TYPE**, which is the shim the classic
path already had (`npc_initial_wire_type` writes 0 and the extended block
carries the real id). Widening the add's type field to 16 is possible — RSProt
models it as `npcInfoBitCount` — but only against a patched client, and the
deob is the authority here.

Three properties make the slot map safe, each asserted and each verified by
mutating the implementation:

| mutation | what the suite said |
|---|---|
| hand every npc the same name | `no two tracked npcs should share one, 14 do` |
| allocate a fresh name on every call | `asking again should give the same name, 15 moved` |
| make `release` a no-op | `no name should outlive the npc it was given to, 4 do` |

The second and third rows are there because the first versions of those checks
did **not** catch their mutations. "Stable" was written as a re-encode, and a
re-encode adds nothing because everything is already tracked, so no name is ever
asked for; it had to be stated against `acquire` directly. "Released" was
written without ever causing a removal, so it passed against a `release` that
did nothing; it had to walk the player out of view first.

### What this cost the selftests

Twenty-one checks failed on the new roster, and every one of them was a test
asserting *content*: "the roster should include a goblin", "…a guard",
"…Turael". Lumbridge stands `goblin_unarmed_melee_1..8` rather than `goblin`,
`deadman_guard_lumbridge` rather than `guard1`, and no Turael — so the subjects
were gone.

The fix is `selftest_require_npc`, which takes the roster's copy when one is
standing where the test asked and spawns its own otherwise. A test about the
engine should not fail when content is corrected. Two further things fell out of
it and are worth knowing, because both were latent:

- **A coordinate is not an identity.** Two mode tests found their subject with
  `type == chicken && x == 3230`, and the roster stands chickens at 3230,3298.
  They now also require `static_spawn < 0` — "no roster entry stood this up",
  which is exactly "the script added it".
- **`npc_setmode(none)` does not stop an npc that still holds a waypoint**, on
  purpose (`Npc.noMode()` is `updateMovement()`; the Inferno's Ancestral Glyph
  depends on it). The follow test passed only because its chicken happened to
  arrive; it now clears the route before asserting the mode holds it still.
- **A pure cardinal approach to a 1×1 destination cannot be walked** —
  `mock230_scene_naive_path` returns the source tile and `npc_walk_to` discards
  it, the way LostCity's `findNaivePath` does. The opplayer2 fixture ended up on
  the player's row and stood still for thirty ticks. It now parks the player
  off-axis, deliberately, rather than inheriting a position from the block above.

## 7. Doing this for another revision

The method is the tool. `tools/gen_spawns.py` takes the cache side from the
content tree, so pointing it at a different tree points it at a different
revision:

```sh

python3 tools/gen_spawns.py \
  --content OSRS-Content/osrsNNN-content \
  --npc-json $RMV/src/mapviewer/data/npc/npc-spawns-osrs.json \

src/build/mock230_pack -v --cache cache.osrsNNN --content OSRS-Content/osrsNNN-content
make -C src mock230-scripts && make -C src test-mock230
```

**Read the report, every time.** It is not a log, it is the finding. The drift
table is the list of ids the target revision has reassigned since the dump, and
it grows with the gap between them — 222 spawns over about two and a half years
here. If it comes back with thousands of rows, the dump is too old for that
cache and the answer is a newer dump, not a looser gate.

Four things change per revision and nothing else does:

1. **`configs/all.<type>.compack` and `configs/all.npc`** — supplied by
   `--content`. That is the entire cache-side dependency; the tool reads no
   binary cache.
2. **`maps/`** — gate 4 uses whatever squares that tree ships, so a cache with
   Varlamore keeps the 776 spawns this one drops.
3. **The `multinpc` graph** — a variant that gains or loses a name changes which
   rows gate 2 can judge. Read fresh from the tree, so this is automatic.
4. **The dump.** Everything above is machinery for surviving the gap between the
   dump's revision and yours; it does not close the gap.

### A different era, not just a different revision

rs-map-viewer already answers this and its answer is the pattern to copy —
`NpcSpawn.ts` picks the file off the cache's identity rather than converting one
roster into another:

| tree | file | why |
|---|---|---|
| `osrs239-content` and any OldSchool cache | `npc-spawns-osrs.json` | one roster covers all of OldSchool; only the *ids* age, which is what §3 is for |
| a rev-254 tree | `npc-spawns-2004.json` (2004scape, MIT) | LostCity's own `maps/*.jm2` carry the same roster by name and are better still |
| rev 549–634–727 | `npc-spawns-2009.json` (2009scape) | `revision > 474` is rs-map-viewer's own cut |

The rule that matters, and the reason there are three files instead of one
converter: **take coordinates across eras, never ids.** A 2004 roster's
`(3209, 3215)` is still where the Cook stands. Its `4626` is not the Cook.

To make a dump where none exists, the RuneLite and OSBot plugins in §2 walk the
world and write the same JSON this tool eats. That is a days-long exercise, and
the reason everyone shares one file.
