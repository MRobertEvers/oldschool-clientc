# Where the npcs stand and what lies on the ground

The rev-239 world roster: how the list was found, how it was checked against
`cache.osrs239` before anything was written down, what it cost, and how to do
the same thing for a different revision.

Result, for the impatient:

| | before | after |
|---|---|---|
| npc spawns | 67 | **23,141** |
| obj spawns | 12 | **2,256** |
| distinct npcs standing somewhere | 38 | 5,599 |
| distinct objs on the ground | 8 | 343 |
| map squares with a roster | 4 (all Lumbridge) | 972 |
| files | 4 hand-authored | 972 generated |

Generated by `tools/gen_spawns.py` into
`OSRS-Content/osrs239-content/server/scripts/areas/world/configs/m<mx>_<mz>.spawn`.
`mock230_pack -v` loads it with **0 errors**.

---

## 1. Why this is a lookup and not a decode

Every other kind of content in this tree comes out of the cache. Spawns cannot,
because an OldSchool cache does not contain any. Where an npc stands, how many
of it there are, and what is lying on the floor is *server* state — the client
is told about an npc when it comes within 15 tiles and never learns that it has
a home tile at all. `cachepack unpack` has nothing to unpack here, which is
exactly why `maps/*.jm2` in LostCity's format has `==== NPC ====` and
`==== OBJ ====` sections that this tree's `unpack` preserves rather than writes
(see `OSRS-Content/README.md`).

So the list has to be *found*, and then it has to be *checked*, because a found
list is a claim about a revision that is probably not the one in front of you.

## 2. What was looked at

Public spawn data for modern OldSchool is all downstream of the same thing: a
dump taken by walking the live game. Nobody re-derives it; everyone re-shares
it. What differs is how recent the dump is, whether it kept display names, and
whether it covers ground items as well as npcs.

| source | what it has | verdict |
|---|---|---|
| [xrsps/xrsps-typescript](https://github.com/xrsps/xrsps-typescript) — `server/data/npc-spawns.json`, `server/gamemodes/vanilla/data/groundItemSpawnData.json` | 24,145 npc spawns with `id`, **`name`**, `x`, `y`, `level`, `direction`, `wanderRadius`; 2,266 ground objs with `id`, `count`, `x`, `y`, `plane` | **used.** The only one found with world-wide coverage of *both* halves, and the only npc dump carrying display names — which is what makes §3 possible |
| [rsmod/rsmod](https://github.com/rsmod/rsmod) — `content/areas/city/lumbridge/.../npcs.toml`, `objs.toml` | 585 npc + 57 obj, **by name**, packed coords, rev-current | **used as the second source.** Lumbridge only, and that is enough to grade the first one (§4) |
| `OpenRune-Server` — `data/cfg/spawns/` | `.gitignore`d; only `item_spawns-example.yml` is committed. `npcs.csv`/`objs.csv` are `id,description`, not spawns | no data |
| [allenkinzalow/npc-spawns](https://github.com/allenkinzalow/npc-spawns), [scape-tools/osbot-npc-dumper-plugin](https://github.com/scape-tools/osbot-npc-dumper-plugin) | RuneLite / OSBot plugins that *produce* a dump by walking the world | **the way to make a new one.** Not a dataset |
| `api.runetopic.com/api/tools/npcs/spawns?revision=N` | a revision-parameterised spawn API — the right shape | dead; TLS no longer validates |
| 2009scape, LostCity, Void | complete rosters for rev 549 / 254 / 634 | wrong era. Coordinates survive an era; **ids do not**, and these predate two decades of id reallocation |
| osrsbox / osrsreboxed | item and monster stats | no coordinates |

Note what is *not* on the list: the OSRS Wiki. It has per-npc location prose and
a map, but no machine-readable coordinate table for spawns, so it works as a
tiebreaker for one npc and not as a source for 24,000.

## 3. The check that matters: a dump carries ids, and ids move

This is the whole reason the work is more than a format conversion.

A spawn in this tree names its npc — `cook 3209 3215 0` — and the name resolves
through `configs/all.npc.compack`. A dump names an id — `{"id": 4626, ...}`. The
conversion is a table lookup and takes one line. The problem is that the lookup
*always succeeds*: id 4626 is some npc in every cache ever built, so a dump from
rev 233 converts cleanly against rev 239 and quietly stands the wrong creature
in the wrong place. That is the failure
`OSRS-Content/.../lumbridge.spawn` was written to describe, found by hand, in a
63-line file.

At 24,145 rows it has to be found by construction. Four gates, in order:

**1 — the id must exist in this cache.** An id past the end of `all.npc` is
dropped. (239 is a superset here: 0 dropped.)

**2 — the name must agree.** The dump's `name` is what a player saw over the
npc's head. This cache's record has a `name=`. If they disagree, the id has been
reallocated and the spawn is wrong. Two refinements make this usable rather than
noisy:

- *Compare the way a person would.* `<col=00ffff>Iceberg</col>` and `Iceberg`,
  `Al Kharid warrior` and `Al-Kharid warrior`, `Tea Seller` and `Tea seller` are
  the same npc. Lowercase, strip markup, strip punctuation. Without this, 2,887
  rows read as drift and the 222 real ones are invisible in the noise.
- *Follow `multinpc`.* A multinpc base has no `name=` at all — it is a shell
  whose varp or varbit picks a variant, and the base id is what a server
  spawns while the variant is what a player sees. So the base has to be checked
  against **every name it can present as**, transitively.

  Skipping that second refinement is not a small miss. Treating "the record has
  no name" as "nothing to check" passes npc **401** as *Turael* standing in
  Burthorpe — and npc 401 in this cache is `tog_light_creature`, a Tears of
  Guthix light creature. 2,518 rows land in this bucket; following `multinpc`
  resolves 1,782 of them into a real comparison and moves 84 spawns from
  "silently accepted" to "rejected as drift".

**3 — a record with no name anywhere is kept.** 736 spawns are of records with
no `name=` and no named variant. There is nothing to contradict, so there is no
basis to drop them; they are counted separately in the report and are the one
place drift could still hide on the npc side.

**4 — the map square must exist.** A spawn on a square `cache.osrs239` does not
ship has no terrain under it. 776 npc and 9 obj dropped, almost all in the
`m56..m66_140..142` band (Varlamore, whose squares this cache does not carry)
plus a stray `m0_0`.

Then: level must be 0..3, and exact duplicates collapse (6 npc, 1 obj).

### The obj half is weaker, and the report says so

The ground-item dump has **no name field**, so gate 2 cannot run on it at all.
Only gates 1, 3 and 4 apply to the 2,266 obj rows. An obj id that was
reallocated between the dump's revision and 239 will be written into this tree
as the wrong item and nothing here will notice. That is stated in the tool's
report rather than hidden, and it is the first thing to fix if a named obj dump
turns up.

## 4. Grading the source against a second one

A gate proves internal consistency. It does not prove the dump is *right*. For
that: `rsmod`'s hand-curated Lumbridge roster, which is name-based,
revision-current, and was built by different people from different data.

Restricted to the six map squares rsmod covers (`m49..m50_49..51`):

```
rsmod spawns in those squares:                585
xrsps spawns in those squares:                585
exact agreement (name + coord + level):       572   97.8%
coordinate agreement:                         578   98.8%
```

Seven coordinates differ, all by one or two tiles (Cook 3208,3215 vs 3209,3215;
Duke of Lumbridge 3210,3224 vs 3212,3220). Six more agree on the tile and pick a
different variant of the same creature — `crow2` vs `crow_lumb_patrol6`,
`farmer2` vs `farmer4`. Nothing in the sample is a different creature.

585 = 585 with 97.8% exact is not two people copying each other's file; the
variant disagreements prove they are not identical inputs. It is two
transcriptions of the same live world, which is the strongest statement
available about a dataset nobody can re-derive from first principles.

## 5. What the roster changed, beyond being 300× bigger

Three npcs the old 4 files spawned have no spawn now, and each is worth naming:

- **`slayer_master_1_tureal`** — Turael. The dump puts him at Burthorpe
  (2931, 3536) under id 401, and 401 is a light creature in this cache. Gate 2
  drops him, correctly, and nothing else in the dump is Turael. Six masters *are*
  spawned (`slayer_master_3`, `_4`, `_6`, `_7`, `_8`, `_9`) and four of those six
  carry triggers in `slayer_masters.rs2` (`_3`, `_4`, `_7`, `_8`), so the panel
  stays reachable; Turael and Aya are the two the scripts bind and the roster
  does not stand. Fixing this needs a source that knows Turael's id in 239, not
  a guess.
- **`doomsayer_normal`** — replaced by `cws_doomsayer` (npc 119) at 3232,3223,
  its multinpc base, which is what the live world actually spawns. The server
  sees the base id, so `[opnpc1,doomsayer_normal]` stopped firing; `tutors.rs2`
  now binds both, with the reason written above the trigger.
- **`goblin_unarmed_melee_in_3`** — the dump uses the `goblin_unarmed_melee_1..8`
  siblings, 60 of them, on the same ground.

Two hand-placed test-world npcs went back to where they belong, which is the
point of the exercise:

- the **Tool Leprechaun** was parked beside Lumbridge castle green because no
  farming patch was loaded. He is now at all 38 real patches.
- **Turael** was parked there too, for the same reason; see above.

Both were marked as test placements in their headers, and both are gone with the
files. The Mage Training Arena guards survive: the dump has them within a tile
of where they were hand-placed (3363,3304 and 3362,3318), which is a small
independent confirmation of both.

The Pest Control misplacement the old header spent forty lines on is gone by
construction — `sos_pest_spider`, `sos_pest_giantspider1` and
`sos_pest_scorpion` are on map square `m33_82` at (2119, 5274), which is Pest
Control's island. `mock230_pack`'s "a name qualified by another content area is
beside the plain one" warning still fires for them, and is now a false positive
for the honest reason: they *are* Pest Control npcs, in Pest Control.

## 6. The one thing this roster does not fit in

`MOCK230_NPC_MAX` is **2048** (`src/net/mock/mock230.h`) and the roster is
23,141. `mock230_world_build_entities` creates every spawn in the tree at boot,
so today it will fill the pool and then log "no free npc slot" for the rest.

Raising the constant does not solve it: the header records that the npc slot on
the wire is 14 bits, so **16,383 is the protocol's own ceiling** on how many
npcs may exist at once, and the roster is above it. A world-wide static roster
therefore cannot be a world-wide *live* roster in this engine — it needs the
spawns to be realised per zone as the player approaches and retired behind them,
which is a server change and not a content one.

The content is complete and correct regardless, and complete is the right state
for it: what to instantiate is the server's decision, and it cannot make a good
one from a list that only has Lumbridge in it. Until that lands, a smaller world
can be had by pointing `MOCK230_CONTENT` at a tree with fewer `.spawn` files, or
by deleting the squares you do not want from
`server/scripts/areas/world/configs/`.

## 7. Doing this for another revision

The method is the tool. `tools/gen_spawns.py` takes the cache side from the
content tree, so pointing it at a different tree points it at a different
revision:

```sh
python3 tools/gen_spawns.py \
  --content OSRS-Content/osrsNNN-content \
  --npc-json ~/…/xrsps-typescript/server/data/npc-spawns.json \
  --obj-json ~/…/xrsps-typescript/server/gamemodes/vanilla/data/groundItemSpawnData.json \
  --out     OSRS-Content/osrsNNN-content/server/scripts/areas/world/configs \
  --report  /tmp/spawn_report.txt \
  --source  "xrsps/xrsps-typescript @ <sha>"

src/build/mock230_pack -v --cache cache.osrsNNN --content OSRS-Content/osrsNNN-content
```

**Read the report, every time.** It is not a log; it is the finding. The drift
table is the list of ids the target revision has reassigned since the dump, and
it grows with the gap between them — 222 spawns over a ~4-revision gap here.
If it comes back with thousands of rows, the dump is too old for that cache and
the answer is a newer dump, not a looser gate.

Four things change per revision and nothing else does:

1. **`configs/all.<type>.compack` and `configs/all.npc`** — supplied by
   `--content`. This is the entire cache-side dependency; the tool reads no
   binary cache.
2. **`maps/`** — gate 4 uses whatever squares that tree ships, so a cache with
   Varlamore keeps the 776 spawns this one drops.
3. **The `multinpc` graph** — a variant that gains or loses a name changes which
   rows gate 2 can judge. It is read fresh from the tree, so this is automatic.
4. **The dump.** Everything above is machinery for surviving the gap between the
   dump's revision and yours; it does not close the gap.

### If no dump exists for the era you need

Rev 254, 634, 727 and the rest have their own rosters in their own era's servers
(LostCity, Void, 2009scape), by name, and those are the right sources for those
trees. The rule that matters is the one this whole document is about: **take
coordinates across eras, never ids.** A 2004 roster's `(3209, 3215)` is still
where the Cook stands. Its `4626` is not the Cook.

To make a dump where none exists, the RuneLite and OSBot plugins in §2 walk the
world and write the same JSON this tool eats. That is a days-long exercise and
the reason everyone shares one file.
