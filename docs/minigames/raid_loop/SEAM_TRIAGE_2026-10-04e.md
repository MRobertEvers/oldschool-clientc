FACTS. The embedded server is "one world, N connections" with TORIRSSERVER_EMBED_CLIENT_MAX = 4 (torirs_server_embed.h), but the client bridge opens only client 0 and the embed has no socket ("no socket anywhere"); a second embed in one process would share file-scope tables (torirs_server_embed.c:68). The standalone `src/build/torirsserver [port]` ticks on a 600 ms wall clock (torirs_server_host.c:37, TORIRSSERVER_TICK_MS) and reads TORIRSSERVER_SAVES, _STAFF_LEVEL, _HOME, _REV, _BIND, _SCRIPTS from the environment like the embed; the client dials it with `[net:boot] transport=tcp host= port=` (manifests/manifest_osrs239.ini:48-50; run.py rewrites that to embed). Determinism: TORIRS_EMBED_CLOCK_MS=20 locks the embedded server's clock to the client's frames; nothing locks a socket server to three clients' frames. Content: a member applies at the notice board (tob_board.rs2 if_button tob_partylist:list -> tob_board_details_open; find the apply/join and accept buttons under tob_partydetails, :441-600) and steps through the door after the leader (tob_party.rs2 oploc1 tob_surface_raid_entrance: "Your party leader has not entered the Theatre yet"; tob_raid.rs2:318 tob_join_raid refuses a different mode, a started room, a full party); the leader's door dialogue is "Is your party ready? Members: N. Mode: X" (tob_party.rs2:483-520); Hard needs %varp6826_tob_completions >= 1 on the account at the door. Every account logs in as its run name with password "test" (run.py QUEST_PASSWORD), and only the first 12 characters of a name seed a run (jbase37).

RULES. (1) One worker at a time; SEARCH DISCIPLINE and OUTPUT DISCIPLINE apply (no command prints more than about 4 KB; no shell command over 8 KB; never a recursive grep or find over OSRS-Content); the editor's Read and Write hooks may time out: use the shell, never loop on a failing tool. (2) Tests do not cheat: setup is bring-alongs only per account (::setlevel, ::give, a fixture .ini may carry a Normal completion for the Hard door); inside a run only read-only readouts. (3) The six room tests under test/raids/ and every test/quests/*.lua are read-only; a quest run through run.py must produce the same ledger as before the change (prove it with cooks_assistant and druid under --no-build, byte-identical ledgers apart from the run name). (4) Nothing in the content is changed to make a party easier to drive; a content disagreement found on the way goes into CONTENT_BUGS.md with its source line. (5) The file lists are exclusive. (6) No `switch` inside a protothread; asserts, not early returns, for a wrong parameter (CLAUDE.md). (8) PRAYER TIMING (owner, 2026-10-04, relayed from the waves session): a protection prayer is checked on the attack's ANIMATION tick, for Jad and for most npcs; a hit whose damage is decided when the projectile lands is the EXCEPTION and needs a pinned source naming that npc. Never move a prayer read from the swing tick to the landing tick; never grade a swing-tick read as a content bug; a bot that switches prayer after seeing the animation is using the wrong technique, not exposing a bug.

Decide, from the code, how three driven clients share one world, and build it. The two candidates: (A) the leader's process hosts the embedded world and ALSO accepts the two other clients over a loopback socket (the embed pump polls a listening socket whose accepted connections become embed clients 1 and 2; the host's tick stays on TORIRS_EMBED_CLOCK_MS, so the leader's run is as deterministic as today, and the followers' clients run at their own frame rate against it); (B) the standalone torirsserver on a free loopback port, three clients with transport=tcp, the server's 600 ms wall clock, and a knob (TORIRSSERVER_TICK_MS from the environment, or a tick-on-demand mode driven by the clients) so a 3-minute room does not take 3 wall-clock minutes per tick budget and so --max-frames still bounds a run. Weigh them by: determinism of the tick log across the three clients (every client's ticklog.tsv must stamp the SAME server tick for the same event: compare an npc_spawn row across the three logs), wall-clock cost per run, how a stall is detected (run.py's heartbeat is per client), and how little of the socket server's loop has to be duplicated. Whichever wins, the proof is a C selftest or a headless run where three clients log in, stand on one tile and each sees the other two players (player_tile rows of the other pids in each log), with the world ticking in lock step. Document the choice and its reasons in DRIVER_NOTES.md (the closer carries it) and the knobs in test/raids/README.md.
