# Raid seam triage, 2026-10-05e (seam26 of the raid loop: the runner camera split -- watch a script without the watcher's camera moving)

The owner, 2026-10-05: "I want to be able to watch the runner run its test, but I don't want the watcher's camera to be affected. ... Have the notion of multiple cameras - one for the script ... the AutomationRunner clicks go through the automation camera, and the PlayerClient clicks go through the PlayerClient camera. ... the goal is for me to be able to watch and debug the automation runner and this should not cause a performance impact when not in use." The design was written with him and is published (https://claude.ai/artifact/FDWBxLAVmDPdt5PxR2erQu, "Runner Camera Split"); this file is its work order and repeats everything a fixer needs. HIS DECISIONS (verbatim): (1) "I want to be able to interact, but it should be clearly indicated and that should be turn on and off button while a script is running"; (2) "Yes, anything that would normally take control of the camera would take control of all cameras (cutscenes, etc - usually server driven effects)"; (3) the runner's right-click menu stays visible, "but perhaps color it differently if it's not the current camera's right click menu"; (4) a picture-in-picture of the runner's view: "Later".

THE FACTS THE DESIGN RESTS ON (read them in the code before changing anything). There is NO camera object: the camera is fields on struct App: `world_camera`, `world_camera_pos` (src/app.h:1147-1148), `orbit` (:1163, the source of truth; `app_world_camera_follow`, src/app/app_camera.c:708, derives the eye every frame), `world_cam_zoom`, `cam_key_*`, `cam_mmb_*`, `camera_unlocked`, `cam_hold`, `cam_script` (CAM_* packets, cutscenes, shake). The PICK is a side effect of the draw at ONE point: the pointer is armed before the render (app_render.c:708), each pickable model is hit-tested after projection and before the face sort (platform_renderer_soft3d.c:1295-1338; GL3 the same), and `app_world_pick_finish` (app_world_click.c:708) fills the one `app->world_pickset`; hover text, the minimenu (app_frame.c:1218, app_minimenu.c:536) and a left click read it next frame. There is ONE pointer: the driver's events and the window's land in the same `input->curr.mouse_x/y` (app_frame.c:188-202). A driver press = project the target analytically (`DrivePointer_ScreenPosition`, no draw) -> mouse_move -> wait `pick_holds` (needs a DRAWN frame stamped at that pixel) -> right press -> `menu_row_find` -> left press (pointer.lua:1690). The driver moves the camera for clicks (`_ensure_visible`, pointer.lua:766, the pose ladder :574) and photographs (`_shot_plan`, :2051; guarded off in a watched client by 63ea41d39). Headless: render skip; a pickset read draws the skipped frame late into a scratch buffer on the software lane, which always exists (`App_RenderSkipCatchUp`, app_render.c:243; app.c:376); `app_capture_fallback_render` (app_plugin_assets.c:320-345) is an EXTRA software re-render with the pick disarmed. Nothing about the camera reaches the server. Readers of the camera outside the renderer: overlays through `app_world_project_at` (app_world_project.c:45), minimap rotation and dots (app_minimap.c), the compass (`UITREE_HOST_GET_CAMERA_YAW`), minimap click by the DRAWN yaw (`MinimapView_Yaw`, app_minimap.c:534), plugin project/draw_tile/hover_tile/hover_entity (torirs_plugin_bridge.u.c), sailing steer (app_wev.c:143), the UI retain signature's camera domain (app_ui_host.c:160), CS2 camera angles (app_world_frame.c:211). Per paint, camera-derived state is written on the ONE `world->painter` and on app: roof level mask, cull span, draw centre, the active occluder set, the sailing view cameras and flatten decision (app_wev.c:746), into the ONE `app->painter_buffer`; `ToriRS_FrameEnd` runs once per draw and drains model load events the GPU lanes learn from (main.c:4410); models without a bind pose accumulate once per draw (app_render.c:196-200); CAM_SHAKE calls rand() at paint (app_world_paint.c:378-472).

THE DESIGN. A VIEW (`struct App_WorldView`) holds what the script and the watcher must not share: the camera pose (orbit, world_camera, world_camera_pos, zoom, cam_hold, projection_scale), the camera input latches (cam_key_*, cam_mmb_*, camera_unlocked), the pointer over the world (world_mouse_x/y and its valid flag), the pick results (world_pickset, world_hover_tile_*), and the right-click menu (`interact.minimenu`: one per view). SHARED, not in the view: the world, the character, the UI tree and layout, the viewport rectangle and emit desc, and the game's scripted camera state (cam_script), which applies to EVERY attached view. Two ROLES: AutomationRunner (what a script's verbs read and write) and PlayerClient (what is presented and what the physical mouse and keys control). `app->views[0]` always exists and is today's fields; `app->views[1]` exists only while a script runs in a windowed client. Headless: views[0] = AutomationRunner, nothing presented, the same path as today. Window, no script: views[0] = PlayerClient. Window, script running: views[0] = AutomationRunner, views[1] = PlayerClient, created as a COPY of views[0] when the run starts (no jump) and copied back into views[0] and freed when it ends (no jump). `app->frame_view` names the view of the frame being built and is set at stage boundaries; readers of `app->world_camera` read `app->frame_view->...`; kernels are untouched (they already take a camera pointer). A WATCHED FRAME: input (physical -> PlayerClient view; driver events -> the runner's pointer), logic, the follow step for each attached view, THEN, only if a verb asked for a pick or a shot, an OFFSCREEN frame built and executed through the AutomationRunner view on the software lane (the catch-up / capture path with the view as a parameter: it fills the runner's pickset and/or the screenshot), THEN the presented frame through the PlayerClient view on the active renderer, picked at the watcher's pointer. The offscreen frame runs FIRST so every piece of shared painter state is left as the presented frame wrote it. THE OFFSCREEN FRAME'S CONTRACT: it does not run ToriRS_FrameEnd or drain load events; it does not advance animation or the no-bind-pose accumulation; it has its own painter buffer; it consumes no rand() (the shake is rolled once per frame and shared); it does not count against the paint-limit step; its pick is armed at the runner's pointer. INPUT: each input event carries its source (physical or runner) and its own position; a gesture is never interleaved with the other source's (while the runner is between a press and its release, or between a right press and the menu row it will press, physical presses wait); hover follows whichever pointer moved last; keyboard focus decides who types. THE INTERACT SWITCH (owner decision 1): a button in the Scripts panel, OFF when a script starts; OFF = the physical mouse and keys are spectator controls (orbit, zoom, hover-inspect the world through the PlayerClient view, the Scripts panel) and game clicks and typing do nothing; ON = they act on the game normally through the PlayerClient view (its pointer, pickset and menu); the state is ALWAYS indicated on the game frame (a badge: "Runner has control" / a warning-coloured "You can interact"), not only in the panel; every watcher action while ON writes a ledger row (the tick and what was done); the switch does not pause the script. SCRIPTED CAMERA (decision 2): CAM_* packets, cutscenes, CAM_FORCEANGLE and shake take every attached view. MENUS (decision 3): the menu that does not belong to the presented view is drawn in a different colour and takes no physical clicks. SCREENSHOTS: a script's shot is the runner's view through the offscreen frame (world, overlays projected through the runner's camera, UI); remove the 63ea41d39 guard in `_shot_plan` once that holds. THE DRIVER attaches: the run wrapper calls `api_drive.view_attach("AutomationRunner")` at start and `view_detach()` at finish or stop; no test file changes; headless creates nothing. NOT IN THIS PASS: a picture-in-picture of the runner's view, a raster-free pick pass, a native second 3D pass on the GPU lanes.

RULES. (1) NO COST WHEN NOT IN USE, proved: with no script attached and in every headless run there is ONE view and no new per-frame work; no branch is added inside projection, raster or any kernel (3rd/toridraw/KERNELS.md's laws); `./launch bench` on the osrs239 world before and after agrees within noise (report the numbers); make -C src check-scan-meter check-tree-walks pass. (2) EVERY TEST RUN IS BYTE-IDENTICAL: cooks_assistant and druid ledgers against build/merge17_check/*_before.tsv, the six Entry rooms' ledgers against their kept ones, _party_smoke green and party_repeat.py --runs 3 AGREE, conformance 100 percent, the quest suite at its baseline. (3) Never open a window on the owner's desktop and never screencapture it; a proof of a watch feature goes through the REAL event path (seam25's TORIRS_SIM_SDL_CLICK_AT and its motion/key siblings; add what is missing) and frames are read as CROPS. (4) CLAUDE.md: asserts not early returns for a wrong parameter (a NULL view is a contract violation), allocation failures assert, no switch inside a protothread, no whole-tree UI walk per frame, no mutation of this tree to prove a test fails, no abbreviated names. (5) The file lists are exclusive; seam order is the order below and each checks the previous seam's fix.<key>.json. (6) One worker at a time; SEARCH and OUTPUT DISCIPLINE (4 KB outputs, 8 KB commands, no recursive grep over OSRS-Content); the Read and Write hooks may time out: use the shell, never loop on a failing tool. (7) Never touch build/orchestrator/worktrees/raid-watch (the owner's viewing copy) or the main checkout.
