# Raid seam triage, 2026-10-06j (seam37 of the raid loop: the IO server launches and manages the clients of a multi-account flow)

The owner, 2026-10-06: "I want the server to be able to launch clients if a leader needs to run a multi-account flow. Add that capability to the IO Server (the same channel that is used to load plugins). The server should have smart management of clients; if the leader client closes or crashes, it should kill the other clients; the leader should be able to send management commands to those clients like 'which account to use', 'what script to run', 'run headless', etc. Design that system, look for oversights and then implement."

FACTS (survey 2026-10-06, file:line in this tree). The IO server is `src/ioserver/io_server_main.c` + `http_server.c` (build target `io-server`, binary `src/build/io_server`), a separate process the launcher starts only when a profile's `services=` names it (tools/launcher/services.py:145-170; `osrs239-web` does, `osrs239-scripts` has `services=` EMPTY, so today the Scripts-tab client reads plugins.ini and tests.ini from local disk, leg 1 of `read_script_item`, platform_x_io.c:603-662, and only falls back to `GET /boot/<path>` over HTTP when `TORIRS_IO_SERVER` is set or the manifest has `[io:boot]`, :177-204). It speaks plain HTTP (`POST /io` IOWire batches, `GET /boot/...`, `/cache/...`, `/status`, `/stats`), one thread, `select()` over a listener and up to 64 clients (http_server.c:30, :554-640), request/response only, no push, NO client identity, binds INADDR_ANY (http_server.c:527). The plugin and script items reach it through `ToriRS_IO_QueueScript(io, PLUGIN_IO_SLOT, path)` -> `PlatformX_IO_LoadItem` -> `case TORIRS_IOK_SCRIPT` (platform_x_io.c:1350) -> local file, else HTTP (platform_x_http.c:244, one connection per item, Connection: close). A party run today is spawned by PYTHON: tools/quest_gate/run.py `run_party` (:1830-1940) starts members with `subprocess.Popen(start_new_session=True)` then the leader; roles come ONLY from env read at boot (net_transport_embed.c:155-229): leader `TORIRS_EMBED_PARTY_LISTEN=<port>` + `_SIZE=N`, member `TORIRS_EMBED_PARTY_JOIN=<port>` + `_SEAT=n`, `_WAIT_S` (60); the leader hosts the embedded world, members host none and reach it over 127.0.0.1 (torirs_server_embed.h:180-210); the link frames are SEAT/READY/TICK/D (protocol 2); a member whose leader dies exits itself (`party_member_lost` -> exit, net_transport_embed.c:530-566); a dead member is dropped like a logout (torirs_server_embed.c:1037); run.py kills members 20 s after the leader exits (:1805, :1138). Accounts: `<base>_p<n>`; the generated wrapper prepends `QD_PARTY = { role, size, names }` (run.py:429). The Scripts tab's Play (torirs_plugin_drive.c `lua_drive_play` :2292-2400, `drive_demand_begin_play` :1572-1648) picks a fresh account, writes its fixture, and `QD.core_run_test` logs out and in; party rows are `available=0` ("needs 3 clients", prepare_scripts.py:162). Nothing in C spawns a process; there is no parent-death handling anywhere; the party link is POSIX only (Windows and web `abort()` in `ToriRSServer_EmbedPartyListen`, torirs_server_embed.c:35-45, :888-893).

DESIGN. (1) THE SERVICE lives in the IO server as a LAUNCH SESSION table and five requests on the plugin channel: the client queues an IO item of a new kind `TORIRS_IOK_LAUNCH` whose path is `launch/<verb>` and whose body is the request (the same `ToriRS_IO_QueueScript` slot and `PlatformX_IO_LoadItem` path the plugin manifest takes; over HTTP it is `POST /launch/<verb>` on the io_server; with no io_server reachable the item answers `unsupported: no io_server` and the tab says so). Verbs: `open` (the leader registers: its pid, its manifest path, its binary path, its saves directory, the party port it will host and the size; the server answers a session id and a SECRET TOKEN that every later request carries), `spawn` (a list of seats, each with: account name and password, the script to run (id, source, fixture, start), `headless` yes/no, extra env; the server builds each member's command line from the LEADER's binary and manifest only, never a path from the request, with `TORIRS_EMBED_PARTY_JOIN=<port> _SEAT=n _WAIT_S`, `--user/--pass`, `TORIRSSERVER_SAVES=<the leader's saves dir>` (the member writes its fresh account's fixture where the leader's world reads it, then logs in), `TORIRS_DRIVE_ON_DEMAND=1`, `TORIRS_DRIVE_AUTOPLAY=<json of the play fields + role/size/names>` (the member's drive issues the same `api.drive.play` the tab issues, on boot, with the account given rather than picked), `SDL_VIDEODRIVER=dummy` when headless (no TORIRS_MAX_FRAMES: a member runs until told), the window args otherwise; `posix_spawn` into the session's own process group; Windows: `CreateProcess` in a job object; web/Android: the service is absent), `command` (leader -> seat or all: `play {fields}`, `stop`, `cheat <line>`, `quit`; the server queues it in the seat's MAILBOX), `mail` (a member polls its mailbox every tick: the server answers the queued commands, and the member posts its STATUS in the same request: state, step, rows, hitpoints, the drive's status table), `status` (the leader reads every seat's last status, pid, alive, exit code), `heartbeat` (the leader calls it every second; carried on `status` too), `close` (clean end: the server sends `quit` to every seat, waits the grace, kills the rest). (2) SMART MANAGEMENT: a reaper runs in the select loop every second: a session whose leader pid is dead (`kill(pid, 0)` fails) OR whose heartbeat is older than 10 s -> SIGTERM its process group, SIGKILL after 5 s, session closed with the reason; a member that exits is recorded with its code and the leader sees it on `status` and may `spawn` that seat again; the server records every session's pids in `build/launch/<session>.pids` so `./launch stop <profile>` and a server restart can reap orphans; on SIGTERM the server kills every session's group; the members ALSO keep their existing own-exit when the party link drops (two independent safeties). (3) THE LEADER HOSTS AT RUNTIME: today a leader only hosts if launched with env; the Scripts-tab client is not. Add a runtime `party host` on the embedded transport (open the listen socket, set the size, wait for seats as the boot path does: net_transport_embed.c) driven by `api.drive.party_host(port, size)`; the lockstep starts when every seat is READY; the leader's own frames-per-tick and the members' must match (the READY check stands). (4) THE DRIVER: `api.drive.launch.open/spawn/command/status/close` (Lua names in full: `t.launch.*` for a script, and the tab's own calls), `api.drive.party()` for a member (seat, size, names from env/link: it replaces the wrapper's `QD_PARTY` so a Play run as a member has the same `QD_PARTY` a run.py member has), `api.drive.play` takes an optional `account` (given by the leader) and a `party` table, `api.drive.quit` (clean process exit for a member told to quit). (5) THE SCRIPTS TAB: a `party=3` row is AVAILABLE when the launch service answers `open`; Play on it: the tab opens a session, spawns seats 2..N headless with the row's script (the owner may tick 'windowed' per seat to watch one), hosts the party, plays role 1 itself through the normal Play path; a PARTY block shows each seat's state, step and hitpoints, with Stop-all and Respawn-seat buttons; the leader's logout, Stop, or the client closing ends the session (`close` on a clean exit, the reaper otherwise). (6) PROFILE: `osrs239-scripts` gains `services=io_server` and the env that makes the client reach it (`TORIRS_IO_SERVER`); the plugin and tests manifests still come from local disk first (leg 1), so nothing the tab reads changes.

OVERSIGHTS LOOKED FOR, AND THE ANSWERS. (a) Security: the launch verbs accept only loopback peers (the server binds INADDR_ANY today: refuse `/launch/*` from a non-127.0.0.1 peer) and only the session's token; the server never executes a path from a request. (b) Orphans if the IO SERVER itself crashes: members exit on their own when the link drops (existing) and the pids file lets `./launch stop` reap; say so in the docs. (c) A member's fresh account must exist in the LEADER's world before the member logs in: the member writes it to the shared saves dir first (same machine); a remote leader is out of scope (say so). (d) Determinism: the tab's party runs in real time and is not graded; run.py's party path (python, virtual clock) is UNCHANGED and stays byte-identical: the test gate does not move to the IO server in this pass. (e) Windows: `CreateProcess` is written but the party link aborts there today: the service answers `unsupported on this platform` rather than spawning members that abort; web and Android have no service. (f) Many windows on the owner's desktop: members are headless unless he ticks windowed; the tab never opens a window the owner did not ask for. (g) The heartbeat and a slow frame: 10 s grace against a leader frame that can stall seconds under load; the pid check is the primary signal, the heartbeat the secondary. (h) A member that never logs in (wrong password, world refused): its status says so within its own boot timeout and the leader's Play reports it instead of waiting forever (the lockstep READY wait is `_WAIT_S`, 60 s: the tab shows the countdown). (i) The io_server's 64-client select limit: one connection per item with Connection: close, a mailbox poll a tick from each member: fine for 3-5 seats; say the number. (j) The existing `[io:boot]` HTTP leg of script reads must not become the default: `TORIRS_IO_SERVER` is set by the profile only for `launch/*`; prove `plugins/plugins.ini` and `tests.ini` are still read locally (the client log line). (k) Headless members and the view split: a member with SDL dummy has one view and no cost (the split's own rule); a windowed member attaches its own runner view like any watched client.

RULES. (1) Proofs are headless and by state, never a real-time play-through watched by eyes (owner: "Never do a real time play through." "Save the visual verification for afterwards."): the end-to-end proof is a headless LEADER with `TORIRS_DRIVE_AUTOPLAY` playing `_play_bloat` as role 1 of a party of 3, whose two members the IO SERVER spawned headless, all three on the virtual clock (`TORIRS_EMBED_CLOCK_MS=20` passed through `spawn` env), to a green ledger on the leader; the lifecycle proofs are C unit tests of the session table (a fake leader pid that exits; a heartbeat that stops; a member that exits; `close`) plus one real run where the leader is SIGKILLed and the members are gone within 15 s (`ps` read before and after). (2) Every kept ledger byte-identical: cooks_assistant and druid, the six Entry rooms, `_play_bloat --party 3` through run.py (5 of 5), `_party_smoke` with `party_repeat.py --runs 3`; conformance 100 percent with the new verbs' rows.
