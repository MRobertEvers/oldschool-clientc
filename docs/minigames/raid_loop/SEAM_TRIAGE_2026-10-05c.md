THE OWNER'S DESIGN RULE FOR THE LIST (2026-10-05): "The client should just query for the available scripts - the server should tell it - in a similar way the client asks for the available plugins." and "The scripts tab should be searchable as well." How the client asks for plugins today: `CreateTask_PluginBoot` (src/plugin/task_plugin_io.c) queues ONE script item through the IO layer for the manifest (`ToriRS_IO_QueueScript(io, PLUGIN_IO_SLOT, "plugins/plugins.ini")`, PLUGIN_MANIFEST_DEFAULT_PATH, resolved under script/ by the IO layer: the filesystem natively, the served script directory on the browser lane), parses its `[plugin:name]` sections (`source=`, `enabled=`), then queues each script the same way. Seam23 instead had the panel read a filesystem index named by an environment variable (TORIRS_SCRIPTS_INDEX -> build/quest_gate/_scripts/index.tsv) that a Python tool (tools/raid_gate/prepare_scripts.py) wrote beforehand. THAT PLUMBING IS REPLACED IN THIS PASS: no environment-pointed index, no prepare step the owner must run. The client asks, through the same IO path as the plugin manifest, for a SCRIPTS MANIFEST (name it by the plugin manifest's convention, e.g. `tests/tests.ini` with `[test:<id>]` sections: `source=`, `suite=`, `title=`, `legs=`, `party=`, `max_frames=`), and fetches a chosen test's source the same way when Play is pressed; whatever serves the plugin manifest serves this one (natively the IO layer's script root, on the web lane the served directory). Decide from the code, and say why, how the manifest comes to exist and stay current without a manual step: the launcher's derived blocks are the existing mechanism for a file derived at launch (`[derived:scripts]` in the world manifest, tools/launcher/profiles.py `generate_resolved_manifest`), so a `[derived:tests]` block that writes the manifest from the tests directories when the profile launches is the likely shape; and how the test sources under test/quests/ and test/raids/ become readable as script items (a second root in the IO layer, or the derived step mirroring them under the script root: pick the one that also works when the script directory is served). THE WRAPPING MOVES INTO LUA for the watched path: today run.py's `write_wrapper_script` writes a standalone Lua file with the test's source embedded verbatim; the driver gains a loader (`QD.run_test(source_text, options)` or the like in quest_driver/core.lua) that does what the wrapper does (the login-grant wait, the setup cheats, the legs) from the raw test source fetched through the IO layer, so nothing has to be pre-generated. run.py keeps its own wrapper unchanged for test runs (byte-identical), and the Lua loader is proved equivalent on cooks_assistant, one legs quest and tob_maiden (same ledger steps and verdicts as the run.py run, apart from the account name). HOT RELOAD (owner, 2026-10-05: "Will scripts be hotreloadable?"): a test script is RELOADED ON EVERY PLAY. Play always re-fetches the test's source through the IO layer (no cached copy of a test source survives between Plays; if the IO layer or the driver caches script items, the watched path bypasses or invalidates it and the proof shows it), so the owner edits test/quests/<quest>.lua or test/raids/<room>.lua, presses Stop then Play, and the edited file runs without restarting the client. For that to hold, the sources must be read where they live: prefer a tests root the IO layer reads directly over a copy mirrored at launch (a mirror goes stale the moment a file is edited; if a mirror is unavoidable on some lane, say so and make Refresh re-derive it). The panel's Refresh button re-queries the manifest so a NEW test file appears without a relaunch (natively: re-derive, then re-fetch). What is NOT hot-reloaded, stated in the docs: a script that is already running is never swapped mid-run (Stop, then Play); the driver's own parts (script/plugins/quest_driver/*.lua, the verbs) are plugin code: find out whether the plugin host's reload seam (src/plugin/torirs_plugin_lua.h :85 "The source bytes are retained for reload", :104) is reachable at run time, and if it is, wire a "Reload driver" button that reloads the quest driver while no script runs; if it is not, say so and leave it (a client restart picks up verb edits).
