# Charged items — charges, Check ops, and depletion

Scope agreed 2026-08-13: **every charged-item family in the cache gets storage,
a working Check op, and correct depletion behaviour.** Drains are wired wherever
the consuming mechanic already exists in this server; where it does not, the
item still holds and reports charges honestly and the ledger records why the
drain is absent. No family is silently skipped.

Reading order: §1 (what a "charged item" is here), §2 (the three storage
classes — this is the part that is per-item research, not one global choice),
§3 (engine gaps that block the work), §4 (the catalog and the wiki ledger),
§5 (the content library), §6 (op binding), §7 (phases), §8 (verification).

---

## 1. What counts, and how the list was built

The ops are already in the cache. `OSRS-Content/osrs239-content/configs/all.obj`
is exporter-owned (see `docs/PORTING_GUIDE.md` §3 and the
`exporter-owns-generated-configs` rule) and already carries `ifop3=Check`,
`ifop4=Uncharge`, `Charge`, `Break`, `Revert`, `Dissolve`, `Dismantle`,
`Detach` on the real items. **Nothing needs adding to the configs.** The ops
exist and are unbound; this work binds them.

A scan of all 33,747 obj records for a Check op paired with a charge-ish op
yields **434 objs across ~182 name-families**. That raw set over-collects and
the catalog tool (§4) curates it:

- **Storage containers** wear a Check op but hold items, not charges — coal bag,
  herb sack, gem bag, plank sack, rune pouches, seed box, log basket, fish
  barrel, meat/fur pouches, looting bag, Bottomless compost bucket. These are a
  *different feature*; the catalog marks them `container` and they are out of
  scope here.
- **Non-charge Checks** — `Magic cape` (daily spellbook switch is a charge, but
  `Check` on `damaged book`, `treat cauldron`, `starter bow`, `Coffin`,
  `Nest box` is not). Marked `not_a_charge`.
- **Charge-ladder duplicates** — `ring_of_dueling_8..1`, Barrows `100/75/50/25`,
  `Black mask (10)..(1)`, `Slayer ring (8)..(1)` are one family each, not eight.

The curated output is `docs/ITEM_CHARGES.md` plus a machine-readable ledger,
both generated by `tools/charged_items_scan.py` (§4). Every row carries a
`status` column so the unimplemented tail stays visible — a silent drop reads
as "covered" when it is not.

## 2. Storage class is per-item research, not one global decision

OldSchool does not have one charge system. It has at least four, and which one
an item uses is a fact about that item that has to be read off the wiki, not
assumed. The ledger records a `storage` column per family and the library (§5)
abstracts over all four so op-binding code never branches on it.

### 2a. `id_ladder` — the charge *is* the obj id

The item id encodes the remaining charges; spending one swaps the slot to the
next id down, and the last one destroys or reverts.

Examples: Barrows (`_100`/`_75`/`_50`/`_25` → broken), `Black mask (10)..(1)`,
`Slayer ring (8)..(1)`, `Ring of dueling (8)..(1)`, `Games necklace`,
`Amulet of glory (4)..(1)`, `Broodoo shield (10)..(1)`, `Explorer's ring 1..4`
(tier, not charge — the *daily uses* are §2c), `Falador shield 1..4` (same).

No storage needed. Precedent already in-tree:
`general/scripts/enchanted_jewellry/ring_of_dueling.rs2`.

### 2b. `item_var` — a counter living on the item instance

The count travels with the object: bank it, trade it, own two with different
counts. Stored with `inv_setvar` / `inv_getvar` (EXTRA 11016/11017), keyed by
obj id, in whichever container holds it.

Examples: Trident of the seas/swamp and their (e) forms, Sanguinesti staff,
Scythe of vitur, Tumeken's shadow, Toxic blowpipe, Abyssal tentacle,
Craw's bow / Viggora's chainmace / Thammaron's sceptre and their (a) forms,
Webweaver bow / Ursine chainmace / Accursed sceptre, Ring of suffering (i/r/ri),
Serpentine/Tanzanite/Magma helm, Bonecrusher, Ash sanctifier, Xeric's talisman,
Pendant of ates, Ring of the elements, Ring of shadows, Pharaoh's sceptre,
Celestial ring/signet, Circlet of water, Amulet of blood fury, Ring of
endurance, Bracelet of ethereum, Soul bearer, Dizana's quiver, Crystal armour /
tools / weapons and Blade of saeldor / Bow of faerdhinen, Arclight / Emberlight,
Bryophyta's staff, Warped sceptre, Tonalztics of ralos, Venator bow, Eye of
ayak, Nature's reprisal, Alchemist's amulet, Giantsoul amulet, Horn of plenty,
Gnomish firelighter, Tome of fire/water/earth (pages), Chronicle (teleport
cards), Infernal axe/pickaxe/harpoon, Iban's staff.

**Blocked by an engine bug — see §3a.**

### 2c. `player_varp` — one account-wide pool, shared by every copy

The count is a property of the *account*, not the item, so a second copy shares
it and banking cannot launder it. Includes the daily-reset family, where the
pool refills on a runeday boundary rather than being bought back.

Examples: the daily-use items — `Explorer's ring` (alchemy + run energy),
`Falador shield` (prayer recharge), `Magic cape` (spellbook switches),
`Kharedst's memoirs`, `Book of the dead`, `Santa's list`; and the genuinely
account-scoped ones the wiki pass will confirm.

Declared as `[name]` blocks in `server/scripts/**/configs/*.varp` with
`scope=perm`, allocated by `tools/ss_allocate.py` into
`OSRS-Content/osrs239-content/pack/varp.alloc` (609 ids allocated today, no
pressure). `mock230_save.c` persists only `scope=perm` varps — a `scope=temp`
charge counter would silently reset on logout.

Daily resets need `date_runeday`. **Blocked by an engine gap — see §3b.**

### 2d. `none` — reports state, holds no count

Items whose Check op reports a boolean or a tier rather than a count (Slayer
helmet's `Check` reports the assignment; the Deadman Sigils report attunement).
Bound so the op answers, backed by no counter.

### The migration this implies

`%scythe_of_vitur_charges` (`skill_combat/scripts/player/gear/scythe_of_vitur.rs2`)
is `player_varp` today and the file's own header says that was a shortcut, not a
finding. The wiki says the scythe's charges are on the item. It moves to
`item_var` in Phase 6 and the private varp goes.

## 3. Engine gaps that block the work

### 3a. Per-item vars are destroyed by container moves — **blocker**

`mock230_container_set` (`src/net/mock/mock230_container.c:388`) calls
`item_clear_vars()` whenever `obj_id` changes, and `mock230_container_add`
(`:516`) never copies vars into the destination. Measured:

| path | vars survive |
|---|---|
| `inv_movetoslot` — equip, `player/scripts/equip.rs2:189` | yes, it swaps the whole `Mock230Item` |
| `inv_moveitem` — unequip `equip.rs2:149`, bank deposit `bank_deposit.rs2:38` | **no** |
| `inv_movefromslot` — `mock230_ops_inv.c:207` | **no** |
| drop → pick up | **no** (ground objs have no var storage at all) |
| save / load | yes — `mock230_save.c:214-247` writes inv/worn/bank/named containers |

So today's crystal armour loses its charges the moment it is unequipped. This is
a live bug independent of this work, and it has to be fixed before `item_var`
can carry anything.

**Fix**: a var-carrying move in `mock230_container.c` used by the `INV_MOVEITEM`
/ `INV_MOVEFROMSLOT` arms of `mock230_ops_inv.c`. Vars move only for unstackable
objs moved as a single unit — a merged stack has no single var to carry, and
charged items are unstackable, so that is the whole domain.

**Stated limits, not fixed**: `MOCK230_ITEM_VAR_MAX = 4` keys per slot (enough:
one charge key per obj); ground objs have no var storage, so a dropped charged
item loses its charges. Both go in the ledger rather than being papered over.

### 3b. `date_runeday` is declared but not implemented

`SS_OP_DATE_RUNEDAY` (4630) exists in `src/serverscript/ss_opcode.h:409` and in
`ss_meta.gen.h`, but `mock230_scripts.c` has no `case` for it — only
`SS_OP_DATE_MINUTES` (`:7699`). Every daily-reset item in §2c needs it. Fix is
the same shape as `DATE_MINUTES`: real time in, runedays since the epoch out.

### 3c. There is no `opworn` trigger

Confirmed: no `[opworn…]` in the content tree and no `SS_TRIGGER_OPWORN` in the
engine. A Check op on a *worn* item arrives as an inventory-button op on the
equipment tab — `[inv_button<N>,wornitems:slotX]`, the seam
`skill_combat/scripts/player/skillcape_boost.rs2` already uses. §6 covers the
generic dispatcher this needs so 182 families do not each hand-write 14 slots.

## 4. The catalog and the wiki ledger

### 4a. `tools/charged_items_scan.py`

Reads `configs/all.obj`, groups objs into name-families, classifies each by its
op set, and emits:

- `docs/ITEM_CHARGES.md` — the human table, grouped by storage class
- `OSRS-Content/osrs239-content/wiki/charged_items.csv` — the ledger:
  `family, obj_ids, ops, storage, max_charges, charge_source, drain_event,
  depletion, wiki_title, status, note`

`status` is one of `implemented` / `charges_only` (holds and reports, drain
mechanic absent) / `container` / `not_a_charge`. The tool is re-runnable and the
diff is how a cache bump gets reviewed.

### 4b. `tools/wiki_item_charges.py`

Cloned from `tools/wiki_fetch.py`'s shape and etiquette — batched
`action=query&titles=` (50/request), `redirects=1`, one request per second, a
descriptive User-Agent with a contact address, no parallelism, and a manifest
that makes a second run a network no-op unless `--refetch` is passed. Writes:

    OSRS-Content/osrs239-content/wiki/items/<title>.wikitext
    OSRS-Content/osrs239-content/wiki/items_manifest.tsv    title, revid, redirected_from, fetch_date

The wikitext is committed so every number in the ledger is auditable offline and
re-derivable, exactly as `wiki/monsters/` already is for npc stats.

### 4c. The parser

Extends `tools/wiki_infobox.py`'s real brace/bracket-depth template parsing (a
regex over the page corrupts on the first nested `{{plink|...}}`) to read
`Infobox Item` plus the free-text charge sections, filling `max_charges`,
`charge_source`, `drain_event`, `depletion`, and — the §2 decision —
`storage`. Where the wiki is ambiguous the ledger says so and the family lands
`charges_only` rather than guessing a number.

## 5. The shared content library

`OSRS-Content/osrs239-content/server/scripts/general/scripts/charges/`

One API over all four storage classes, so binding code never branches:

    ~charges_get(obj $obj, inv $inv, int $slot)(int)
    ~charges_set(inv $inv, int $slot, obj $obj, int $n)
    ~charges_add(inv $inv, int $slot, obj $obj, int $n)(int)
    ~charges_drain(inv $inv, int $slot, obj $obj, int $n)(boolean)   // true = depleted
    ~charges_max(obj $obj)(int)
    ~charges_report(obj $obj, int $slot)                              // the Check message
    ~charges_deplete(inv $inv, int $slot, obj $obj)

`~charges_deplete` implements the three depletion shapes the wiki actually uses,
which is the "breaking / run out of charges" half of the task:

1. **revert** — swap to the uncharged obj (`Trident of the seas` →
   `Uncharged trident`, `Scythe of vitur` → `Scythe of vitur (uncharged)`,
   `Blade of saeldor` → `(c)` inversion, crystal → seed)
2. **destroy** — the item is consumed (`Dodgy necklace` crumbles,
   `Ring of dueling (1)` crumbles to dust, `Abyssal tentacle` → `Kraken tentacle`
   is a revert, but `Binding necklace` is a destroy)
3. **degrade-step** — advance the id ladder (`Barrows 100 → 75 → 50 → 25 →
   broken`, `Black mask (10) → (9)`)

The per-family data (max, storage class, depletion shape, target obj, message
wording) lives in **one table**, generated into a `.dbtable`/`.dbrow` pair or a
`.constant` block from the §4 ledger — not in 182 hand-copied `switch_obj`
blocks. `skill_combat/configs/levelrequire.dbtable` + `tools/gen_levelrequire_dbrow.py`
is the in-tree precedent for a generated script-readable index, including the
selftest leg that walks the whole table so the two forms of one fact cannot
drift apart.

The probabilistic-break family (Dodgy necklace, Expeditious bracelet, Bracelet
of slaughter, Flamtaer bracelet, Ring of pursuit, Amulet of bounty, Efaritay's
aid, Gloves of silence, Binding necklace) is `item_var` storage plus a drain
fired from a skill event rather than a combat swing, and depletion shape
`destroy`. Same library, different hook.

## 6. Op binding

- **Inventory Check** — `[opheld3,<obj>]` (the op index comes from the record's
  own `ifop3=Check`; a few families use a different index and the ledger carries
  the real one). Body is `~charges_report`.
- **Inventory Uncharge / Charge / Break / Revert / Dissolve / Dismantle** —
  bound per family from the ledger's op column.
- **Worn Check** — one generic `[inv_button<N>,wornitems:slotX]` dispatcher that
  resolves the worn obj and calls the same `~charges_report`, rather than 182
  families × 14 slots of copy. See §3c.

Binding is generated where it is mechanical and hand-written where the wiki says
something specific, following the same split
`general/scripts/enchanted_jewellry/` already uses.

## 8. Verification

- `::chargesrun`, a `[debugproc]` modelled on
  `skill_combat/scripts/player/gear/gear_selftest.rs2` — one FAIL line and stop,
  or `chargesrun OK — N checks passed`. Covers each storage class, each
  depletion shape, and the equip/unequip/bank round-trip that §3a fixes.
- `make -C src mock230 && ./src/build/mock230 --selftest`, run with **no env
  set**. The `MOCK230_REV=osrs239` lane has ~205 pre-existing failures unrelated
  to this work (`mock230-selftest-two-lanes`); a green run means the no-env lane.
- New engine cases get coverage in `src/net/mock/test/`.
- A selftest leg walks the whole generated charge table and asserts the C-side
  and script-side agree, so the generated data cannot drift from the ledger.
