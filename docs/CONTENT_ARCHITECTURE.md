# Content architecture — unifying the cache tools and the server tree

Two lines of work landed in `OSRS-Content/osrs239-content/` from opposite ends:

- **`cachepack`** (`3rd/rscache/tools/cachepack/`) turns a cache into an editable
  tree and back. It owns `pack/`, `configs/`, and the asset directories.
- **The mock server** (`src/net/mock/`, `src/serverscript/`) reads a LostCity
  content tree. It owns `server/pack/` and `server/scripts/`.

They now share one directory and one id namespace, and nothing states the
contract between them. This document is that contract: what the split *should*
be, why the current one is not it, and what has to change so that absorbing a
new cache is a routine step rather than a merge conflict.

The reference is LostCity's `content/` + `engine/tools/pack`, which solved the
same problem five revisions in a row (`content/scripts/_unpack/` holds 225, 244,
245 and 254). Its answers are used verbatim where they transfer, and where they
do not — LostCity authors its cache and this tree receives one — the difference
is stated rather than papered over.

---

## 1. The question that motivated this

> Why are there two `varp` packs?

Because `pack/varp.pack` is a **function of the cache** and cannot express what
`server/pack/varp_mock.pack` needs to say. Concretely, unpacking `cache.osrs239`
into an empty tree produces:

```
43=com_mode
115=bankcert
843=randomhitsound
1105=wilderness_statistics
```

— those are the cache's own gameval names, not anybody's choice. The server
needs three things that file structurally cannot hold:

| need | example | why `pack/varp.pack` can't |
|---|---|---|
| a **second** name for a named id | `115=bank_withdrawnotes` beside `bankcert` | `LC_Pack` is `names[id]` — one name per id |
| an **override** of a cache name | `843=varp_weapon_category`, because this world repurposed it | `cachepack` regenerates the file; the override would be reverted or, worse, kept and indistinguishable from a cache name |
| a name for something the cache never names | `stat.pack`, `category.pack` | no gameval archive to seed from |

So the *instinct* behind `server/pack/` is right. What is wrong is that it was
applied to exactly one namespace, and the same three needs elsewhere were solved
by hand-editing the machine-owned file instead:

```
$ grep -v '=interface_' pack/interface.pack | head -3
12=bankmain          # authored, spliced into a cachepack-generated file
15=bankside
84=equipment_stats
```

`pack/varp.pack` and `server/pack/varp_mock.pack` are not two namespaces. They
are **two layers of one namespace**, and that is the abstraction the tree is
missing.

## 2. What LostCity actually does

Four mechanisms, and they are separable.

### 2.1 One `pack/`, three id classes

LostCity has a single flat `content/pack/` — no `server/pack/`. The distinction
it makes is not *where the file lives* but **who is allowed to choose the id**,
declared per type in `PackFile.ts`:

```ts
export const NpcPack   = new PackFile('npc',   validateConfigPack, '.npc',   true);
export const EnumPack  = new PackFile('enum',  validateConfigPack, '.enum');
export const CategoryPack = new PackFile('category', validateCategoryPack);
```

That trailing `true` is `transmitted`.

| class | types | build behaviour |
|---|---|---|
| **transmitted** | npc obj loc seq spotanim varp varbit idk flo | the client's cache fixes the id. A name with no id line is a **hard error** under `BUILD_VERIFY`. Never auto-allocated. |
| **server-allocated** | enum struct param inv dbtable dbrow hunt mesanim varn vars script | the id space is the server's. The build **registers `pack.max++`** for any new name and rewrites the pack file, which is therefore a *lockfile* keeping assignments stable. |
| **derived** | category | fully regenerated by crawling `category=` out of every `.loc`/`.npc`/`.obj`. Never authored. |

### 2.2 One record, two encoders

`readConfigs()` in `PackShared.ts` parses one `[name]` block and hands it to a
packer that returns **both** halves:

```ts
export type ConfigDatIdx = { client: PackedData; server: PackedData };
```

The client half is written into `config.jag` (the cache the client downloads);
the server half into `data/pack/server/<type>.dat`. `hitpoints` and `respawnrate`
never reach the client; `model` and `recol` never need a second copy on the
server. **There is no "server config type" and "cache config type" — there are
server *fields* and client *fields* of one record.**

For the nine transmitted types the client half is then checksummed against a
constant:

```ts
(client, _server) => Packet.checkcrc(client.data, 0, client.pos, 1077655221)  // npc
```

That is the gate that says "we did not change what the client sees".

### 2.3 The bump loop is a review queue, not a patch

`Unpack.ts` reads the **new** cache and diffs it against the **currently built**
one, writing under `content/scripts/_unpack/<rev>/`:

| file | contents |
|---|---|
| `all.<type>` | ids present in the new cache and not the old — genuinely new records |
| `all.<type>.merge` | ids whose unpacked text differs, new block then old block, `// --------` separated |
| *(nothing)* | ids that are identical |

Names are seeded but never overwritten:

```ts
for (let id = 0; id < sourceIdx.size; id++) {
    if (!pack.getById(id)) pack.register(id, `${type}_${id}`);
}
```

The queue is **inside** `scripts/`, so its `[name]` headers are crawled into the
packs immediately (ids get reserved) while `BUILD_VERIFY_FOLDER` exempts it from
the "configs live in `configs/`" rule. New ids exist before anyone decides what
they mean. A human moves blocks out of `_unpack/` into real content.

### 2.4 Nothing is transcoded twice

Models keep their names across a bump by back-filling from the *new* loc configs,
and only for ids past the old cache's model count (`unpackModelNames`, gated on
`model < modelRenameOffset`). Work already done is never redone.

## 3. How this tree diverges

Five divergences. Each is evidenced, and each has a cost that has either already
been paid or is queued up for the next cache.

### 3.1 `pack/` has three writers with three write policies

| file | written by | policy | provenance marker |
|---|---|---|---|
| `pack/npc.pack` | `cachepack unpack` | regenerate, preserve existing names | none |
| `pack/component.pack` | `tools/gameval_import.py` | **truncate and rewrite** | header comment |
| `pack/param.pack` | both | cachepack regenerates; the names are hand-authored | 58 comment lines |
| `pack/interface.pack` | `cachepack unpack` | regenerate; 34 names hand-spliced | none |

`gameval_import.py` opens its outputs with `"w"` and maps eleven namespaces, nine
of which `cachepack` also owns:

```python
PACK_FOR_NAMESPACE = { "npcs": "npc", "items": "obj", "objects": "loc",
                       "sequences": "seq", "spotanims": "spotanim", "inv": "inv",
                       "varp": "varp", "varbits": "varbit",
                       "interfaces": "interface", "components": "component",
                       "varcs": "varc" }
```

and `tools/gameval_import.names` currently requests eight of them — 39 `npcs`,
36 `items`, 12 `objects`, 23 `sequences`, 21 `varbits`, 11 `varp`, 34
`interfaces`, 116 `components`. So the documented command in
`docs/mock230_content.md` §5:

```sh
tools/gameval_import.py --names tools/gameval_import.names \
    --out OSRS-Content/osrs239-content/pack
```

**truncates `pack/npc.pack` from 16,292 lines to 39**, `varp.pack` from 5,705 to
11, and so on. A following `cachepack unpack` refills them from the cache's own
gamevals — which silently *reverts* every alias the import just made. Neither
ordering is correct, and the tree survives today only because OpenRune and the
cache happen to agree on the names actually requested (both call npc 3028
`goblin`, npc 3254 `guard1`, varp 43 `com_mode`).

### 3.2 `cachepack unpack` destroys authored prose in packs it owns

`cp_names_save()` writes every `CP_TYPE_COUNT` pack unconditionally, and
`lc_pack_save()` emits nothing but `id=name` lines. Measured, on a copy:

```
$ cp pack/param.pack $PROBE/pack/param.pack
before: 58 comment lines, 2692 total
$ cachepack unpack --cache cache.osrs239 --rev osrs239 --src $PROBE --types param
after:  0 comment lines, 2634 total
```

The names survived (preserve-existing works). The *evidence for the names* —
which is the whole reason `docs/mock230_content.md` §4 can be trusted — did not.
`param.pack`'s header is the single most load-bearing comment in the tree: it is
the record of which param-id claims were checked against a cache and how.

### 3.3 The "invented" server param ids are not invented

`pack/param.pack` states:

> `2000+` invented by this server for things no cache states — `death_drop`, the
> combat animations, `respawnrate`. **They live above every real param id so they
> cannot collide with one.**

`cache.osrs239` has **2,634 param records covering ids 0–2633**. Every server id
— 2000–2008 and 2100–2105 — is a param the cache already defines. `param 2100`,
which `mock230_pack --cache-out` writes `hitpoints` into, exists.

The practical blast radius is small (the derived cache is consumed by our own
tools, and OSRS params are mostly server-side there too), but the *method* is
the problem: a hand-picked "surely nothing is up here" constant is not an
allocator. LostCity's `pack.max++` reads the high-water mark from the pack file
and cannot make this mistake.

### 3.4 Three symbol loaders, three tables, in two languages

| consumer | source | mechanism | coverage |
|---|---|---|---|
| `cachepack` | `<src>/pack/*.pack` | `cp_names_load`, one per registered type/asset | 20 types + assets; **cannot see `server/pack/`** |
| `sscompile` | `--pack DIR` (repeatable) | `SSC_SymbolsLoadPackDir` + `kind_for_pack()` filename table | 21 filenames |
| `mock230` | hardcoded `k_packs[]` | `mock230_content.c` | **14 files, 13 kinds** |

`server/pack/category.pack` is loaded by the compiler and not by the runtime.
That is currently harmless — a category id is baked into bytecode at compile
time, so the runtime only needs the number off the obj record — but it means the
two tables agree by accident, not by construction. Adding a namespace today is
three edits in two languages plus, sometimes, `gameval_import.names`.

### 3.5 A record exists three times and nothing makes the copies agree

For npc 3028 there is:

1. the bytes in `cache.osrs239` — what the client reads, and what
   `mock230_npcinfo.c` decodes at boot for combat params and wear positions;
2. `configs/all.npc`'s `[goblin]` block — 8.6 MB of cachepack text that **no
   runtime reads**; its only consumer is `cachepack pack`;
3. `server/scripts/areas/lumbridge/configs/lumbridge.npc`'s `[goblin]` overlay —
   a different key set in a different grammar, read by `mock230_content.c`.

Two independent paths write a derived cache — `cachepack pack` (from 2) and
`mock230_pack --cache-out` (from 1 + 3) — **and they do not compose**. You cannot
`cachepack pack` a tree whose npc overlays live in `server/`, and
`mock230_pack --cache-out` re-implements record encoding for the two field
families it knows about. This is the deepest of the five, and it is exactly what
LostCity's two-encoder design exists to prevent.

## 4. The unified model

> **One record. One namespace. Layers, not directories. The cache is an input,
> never the source of truth for anything a human typed.**

The current tree splits on filesystem location. The split it wants is on three
independent axes that got collapsed into one:

| axis | question | values |
|---|---|---|
| **A — id authority** | who may choose the number? | `cache` · `server` · `protocol` |
| **B — name authority** | where does the text come from? | `cache` (gameval) · `authored` · `derived` · `imported` |
| **C — field scope** | does the client see it? | `client` · `server` |

`server/pack/` conflated A and B; `server/scripts/**/configs/` conflated B and C.

### 4.1 Namespaces: one directory, two layers

```
pack/<ns>.pack      layer 0 — machine-owned. Regenerated wholesale by cachepack
                              from the cache's gameval table. Never hand-edited.
                              No comments (they will be eaten; that is fine now,
                              because nothing authored lives here).

names/<ns>.pack     layer 1 — human-owned. Never machine-written. Holds exactly
                              the three things layer 0 cannot express:
                                · alias      a second name for a named id
                                · override   replace layer 0's name for an id
                                · fill       name an id layer 0 leaves unnamed
                              Comments live here, because this is where the
                              claims that need justifying live.
```

`server/pack/varp_mock.pack` becomes `names/varp.pack`. `server/pack/stat.pack`
and `server/pack/category.pack` become `names/stat.pack` and
`names/category.pack` — no `pack/stat.pack` exists to layer over, which is
correct and needs no special case. The 34 hand-spliced lines in
`pack/interface.pack` and the 58-comment header of `pack/param.pack` move to
`names/interface.pack` and `names/param.pack`.

The payoff is that **layer 0 becomes disposable**. Today `pack/npc.pack` is the
accumulated residue of every unpack ever run and nobody can tell a leftover from
an authored name; after the split, `rm -rf pack/ && cachepack unpack` is a safe,
idempotent operation and every surviving name in `names/` is one a human wrote.

Resolution rules, and they are the whole of the semantics:

- layer 1 wins for `id → name` (the canonical name); layer 0's name still
  resolves for `name → id` (so `bankcert` and `bank_withdrawnotes` both work).
- a layer-1 name that collides with a *different* id's layer-0 name is a **load
  error**, not a silent shadow. This is the `%bank_withdrawnotes` hazard the
  current `varp_mock.pack` header describes in prose.
- `varp`/`varbit`/`varn`/`vars` share one RuneScript name domain, so collisions
  across those four are errors too — LostCity checks exactly this in
  `packConfigs()`.

### 4.2 One register, read by everything

`content.ini` at the tree root, alongside `meta.ini`:

```ini
[namespace:varp]
ids    = cache            ; cache | server | protocol
names  = cache            ; layer 0 source
source = config:varp      ; what cachepack regenerates it from

[namespace:param]
ids    = cache
names  = cache
alloc  = server           ; server-allocated ids start at the cache high-water mark

[namespace:stat]
ids    = protocol         ; UPDATE_STAT carries this index; not the cache's to move
names  = authored

[namespace:category]
ids    = cache            ; obj config opcode 94 states the number
names  = authored         ; no gameval archive names them
zero   = reserved         ; category 0 is "unstated" and must never be a name

[namespace:component]
ids    = cache
names  = imported:gameval_import  ; foreign rev — every line is a claim
```

Three consumers, one table:

- `cachepack` reads it to know which packs it may rewrite. It already links
  `3rd/ini`. It must refuse to write any pack whose `names` is not `cache`.
- `sscompile` reads it instead of the `kind_for_pack()` filename table.
- `mock230` reads it instead of `k_packs[]`.

Adding a namespace becomes one `[namespace:*]` block. That is the "future proof
for new server features" requirement, discharged.

### 4.3 Config layers and the field register

Keep `configs/all.<type>` as layer 0 — it is machine output, one file per type
is diffable, and 16,292 files per type is not. Overlays stay per-file under
`server/scripts/**/configs/`, because those are authored.

The merge is by `[name]`, key by key, and each key declares its scope in a
**field register** per type:

```ini
[npc.name]          scope = client
[npc.model]         scope = client
[npc.hitpoints]     scope = server   client = param:2100
[npc.respawnrate]   scope = server   client = param:2104
[npc.attackrate]    scope = server   client = param:14     ; the cache already has it
[loc.next_loc_stage] scope = server  client = param:2007
```

The merged record then feeds two encoders, LostCity's `{client, server}`:

- **client encoder** → `cachepack pack` → the cache record. A `scope=server` key
  with a `client=` mapping is written as that param; one without is dropped.
- **server encoder** → the mock's in-memory def, all keys.

Three things fall out:

1. `mock230_pack --cache-out` **disappears**. `bake_npc_params()` and
   `bake_loc_params()` are ~100 lines re-deriving what the register now states,
   and their `BakedParam` table becomes the `client =` column.
2. `configs/all.npc` stops being write-only. It is layer 0 of the record the
   server actually uses, so the "three copies of npc 3028" collapse to one
   source with two views.
3. Adding a server feature is a register row. Adding a field a newer cache
   introduced is a `cachepack` decoder change plus a register row with
   `scope=client`. Neither touches C control flow.

`mock230_content.c`'s per-key `strcmp` ladders and its "accepted and ignored"
behaviour both become table lookups against the register — and "ignored" becomes
"declared `scope=client`, so the overlay is patching the cache", which is a
different and much more interesting thing to report.

### 4.4 Server-allocated ids get an allocator

Where the server needs an id the cache does not define, take LostCity's rule
literally: **`max + 1` off layer 0**, recorded in `names/<ns>.pack`, stable
forever after. For `param` on `cache.osrs239` that is 2634, not 2000.

This is the one place the current tree guessed, and §3.3 is what the guess cost.

## 5. The bump loop

`cachepack unpack --compare` already emits the LostCity queue —
`all.<type>` for new ids, `all.<type>.merge` for changed records,
`stale.<type>.pack` for names whose ids vanished. Two things turn it from an
8 MB reading exercise into a gate.

### 5.1 Filter the diff by what `server/` actually references

1,877 changed npcs is noise. The six that a `.rs2` or an overlay names is the
work. Compute the **symbol closure of `server/`** — every name referenced by any
script, overlay, `.enum`, or the engine's own `mock230_ids.h` table — and
intersect it with the diff:

```ini
; configs/_unpack/osrs245/report.ini
[npc]
new              = 412
changed          = 1877
referenced       = 47      ; of which server/ names
referenced_changed = 2     ; ← the actual work
  goblin           ; combatlevel 2 -> 3
  guard1           ; size 1 -> 2
stale_referenced = 0
```

### 5.2 Pin the referenced surface

```
names/pins.ini
[npc]
goblin = 3028 ; name=Goblin combatlevel=2 size=1 param[10]=-15
guard1 = 3254 ; name=Guard   combatlevel=21 size=1 param[14]=4
```

Every symbol `server/` references, pinned to its id plus a fingerprint of the
cache fields the server depends on. `mock230_pack` regenerates and diffs it;
a mismatch is a non-zero exit. `test-mock230` already pins resolved ids to the
numbers they had as `#define`s — this generalises that from a dozen ids in C to
the whole referenced surface in content, which is where it belongs and where a
cache bump can actually see it.

Id drift is the stated risk of the whole loop ("same display name, different
id" — `goblin` 3028 vs 655). This makes it mechanical.

### 5.3 The loop, after

```sh
# 1. absorb — rewrites pack/ and configs/, never touches names/ or server/
cachepack unpack --cache cache.osrsNEW --rev osrsNEW \
  --src OSRS-Content/osrs239-content --assets \
  --compare cache.osrs239 --compare-rev osrs239

# 2. read one file
$EDITOR OSRS-Content/osrs239-content/configs/_unpack/osrsNEW/report.ini

# 3. gate
make -C src mock230-pack && src/build/mock230_pack --cache cache.osrsNEW \
  --content OSRS-Content/osrs239-content       # pins + symbol closure + overlays
make -C src mock230-scripts test-mock230

# 4. emit — one packer, overlays included, no second bake step
cachepack pack --src OSRS-Content/osrs239-content --base cache.osrsNEW \
  --out /tmp/cache.patched --assets
```

Step 4 replacing `mock230_pack --cache-out` is the visible sign that §3.5 is
fixed.

## 6. Migration

Staged so each step is independently testable and none is a flag day.

| # | step | touches | unblocks |
|---|---|---|---|
| 1 | ~~`names/` layer~~ — **done for the runtime and the compiler**; see §6.1 below. `cachepack`'s `cp_names_load` still does not read layer 1, and the 34 interface lines + `param.pack` header have not moved yet. | all three loaders | §3.1 §3.2 — makes `pack/` disposable |
| 2 | `content.ini` register; delete `k_packs[]` and `kind_for_pack()`. | same three | §3.4 |
| 3 | Teach `gameval_import.py` to write `names/`, merge rather than truncate, and refuse to write `pack/`. | one script | the live landmine in §3.1 |
| 4 | Server id allocator off layer-0 `max`; renumber the 2000-block params. | `names/param.pack`, `mock230_pack` | §3.3 |
| 5 | Field register + `{client, server}` encoders; overlays become config layer 1. | `mock230_content.c`, `cp_pack.c` | §3.5 |
| 6 | `report.ini` + `names/pins.ini` + the symbol closure in `mock230_pack`. | `cp_unpack.c`, `mock230_pack.c` | §5 |
| 7 | Retire `mock230_pack --cache-out`; `cachepack pack` covers it. | delete ~150 lines | — |

Steps 1–3 are mechanical and remove the two ways the tree can currently be
corrupted by running a documented command. Steps 5 and 7 are the real
architectural change and depend on 1–4.

`src/content/` is the natural home for the merged loader (steps 1, 2, 5) —
today the same job is done twice, in `src/serverscript/ssc_symbols.c` and
`src/net/mock/mock230_content.c`. `cachepack` stays independent of `src/`
because it is a vendored-library tool; `content.ini` is the contract between the
two repos, and a small ini parser is already vendored at `3rd/ini`.

## 7. What deliberately does not change

- **Assets are not transcoded.** Models stay `.model`, not `.ob2`; the
  `EXCEPTIONS.md` A5 argument is unaffected by any of this.
- **`configs/all.<type>` stays one file per type.** Per-record files are right
  for authored content and wrong for 16,292 machine-written blocks.
- **`server/scripts/` keeps LostCity's grammar exactly.** The value of matching
  the reference is that a config pastes in either direction; a field register
  changes who *reads* a key, not how it is spelled.
- **`cachepack` never reads `server/`.** "Server scripts do not get encoded into
  the cache" stays true by construction. The field register lives at the tree
  root, not under `server/`, precisely so this holds.
- **Arithmetic stays in C.** The `+8` in the effective-level formula is the
  formula, not a tunable. `docs/mock230_content.md` §2's three-way split —
  storage ceilings, protocol encodings, arithmetic — is unchanged.

## 6.1 Step 1, as landed — and the bug it found

The `names/` layer is live in `mock230_content.c` (runtime) and, via
`--pack names`, in `sscompile`. `PackEntry` carries a `layer`, both layers
resolve `name -> id` with authored first, layer 1 wins `id -> name`, and
`validate_name_layers()` enforces the two rules from §4.1. The tree now has:

```
names/varp.pack      was server/pack/varp_mock.pack
names/stat.pack      was server/pack/stat.pack
names/category.pack  was server/pack/category.pack
```

`server/pack/` is gone. The old paths are still read at layer 1 so a tree that
has not moved still loads.

**The collision rule found a shipped bug on its first run.** Four names were
both a varp and a varbit:

```
`bank_withdrawnotes` is both varp 115 and varbit 3958
`bank_insertmode`    is both varp 304 and varbit 3959
`bank_quantity_type` is both varp 1666 and varbit 6590
`bank_requestedquantity` is both varp 1667 and varbit 3960
```

`varp_mock.pack`'s header described this as *deliberate* — "`%bank_withdrawnotes`
resolves varp-first, so dropping the alias would silently repoint it at the
varbit" — treating the varbit as the wrong answer. It is the right one, and
`bank.rs2`'s own header says so three paragraphs earlier: *"writing either as a
varp destroys the other"*.

`resolve_variable` in `ssc_compile.c` tries VARP before VARBIT, so every bank
setting the content wrote compiled to a whole-varp write:

| script | emitted | should have been | damage |
|---|---|---|---|
| `[proc,openbank]` | `POP_VARP 115 = 0` | `POP_VARBIT 3958` | wipes `bank_currenttab`, varp 115 bits 4..7 |
| `[if_button,bankmain_swap/insert]` | `POP_VARP 304` | `POP_VARBIT 3959` | wipes `bank_requestedquantity`, varp 304 bits 1..31 |
| `[if_button,bankmain_qty_*]` | `POP_VARP 1666 = N` | `POP_VARBIT 6590` | `bank_quantity_type` reads bits 2..4, so the mode never took |
| `[if_button,bankmain_qty_x]` | `POP_VARP 1667` | `POP_VARBIT 3960` | varp 1667 holds nothing; the real home is varp 304 |

So opening the bank reset the current tab, toggling insert mode discarded the
pending quantity, and the quantity buttons did not change the quantity. All
three shipped, and none of them is visible in a passing test: the bank
selftests exercise `mock230_bank_handle_button` (the C fallback), while the
script claims the trigger first at runtime.

Removing the four aliases repoints every one at its varbit, which patches its own
bit range. `test-mock230` now asserts the tree loads with zero content errors and
that those three names resolve as varbits and *not* as varps, so the aliases
cannot come back quietly.

The general lesson is the one §4.1 already argued: **the hazard was written down
in prose in the very file that caused it.** A comment saying "this is subtle,
be careful" is a check that never runs.
